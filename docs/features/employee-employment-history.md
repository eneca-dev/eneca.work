# История состава отделов и загрузки по датам

Задача: feature-VN-05. Хранение, кадровые операции и подключение графика подготовлены к ревью и проверены локально. В рабочей БД функция не включена.

## Цель и границы

Исправить исторический расчёт на вкладке «Отделы»: кадровые события учитываются с датой действия. Загрузки остаются плановыми назначениями; наличие полосы не является доказательством фактически выполненной работы.

Основной результат — корректные дневные и месячные графики отделов, команд и сотрудников. Существующие назначения и их идентификаторы сохраняются. Для «Занятости», выбора исполнителей, авторизации и отчётов требуется проверка совместимости; полная переработка всех аналитических отчётов не включается автоматически.

## Подтверждено в локальном коде

- DepartmentRow и TeamRow вычисляют одну сумму employmentRate для всего диапазона.
- getDepartmentsData распределяет все загрузки по текущим final_department_id/final_team_id.
- Employee содержит одну ставку, без кадровых периодов.
- user-dialog вызывает services/org-data-service.updateUser; существуют и другие пути изменения состава (админка команд, RPC, создание пользователя).
- API удаления пытается удалить profiles и Auth-пользователя. Проверка живой БД 19.11.2026 показала FK loading_responsible → profiles без ON DELETE SET NULL (обычный NO ACTION). Значит актуальная БД должна блокировать удаление профиля с такими ссылками. Прежний вывод о гарантированном обнулении ответственного по старому дампу не подтверждён; конкретные случаи исчезновения загрузок нужно исследовать отдельно.
- Проверка каталога живой БД 19.11.2026 не выявила готовой кадровой истории. В profiles нет кадровых дат, её триггеры не сохраняют прежние значения. work_schedules пуста и описывает расписание по дням недели. assignment_audit относится к заданиям между разделами. Таблицы project_management.airtable_users_2 и airtable_users_gup содержат отделы и команды, но не даты кадровых событий.
- В profiles есть триггер очистки межотдельных грантов при смене отдела и проверки целостности команды/отдела. Их поведение нужно учитывать при атомарном переводе.

## Предлагаемое продуктовое поведение

1. Дата приёма — первый рабочий календарный день сотрудника в системе учёта; фактический расчёт использует рабочий календарь.
2. Дата увольнения в UI — последний день работы, включительно.
3. Перевод и смена ставки действуют с указанной даты. Старое назначение заканчивается перед этой датой.
4. Уволенный остаётся доступен в историческом просмотре, но не в списке новых назначений на даты вне периода работы.
5. Полоса, пересекающая кадровую границу, учитывается по соответствующим периодам без физического разрезания исходной записи loadings.
6. Загрузки вне периода работы не удаляются автоматически: показывается конфликт данных; они не входят в показатель загрузки действующего состава. Согласовать это правило до реализации.
7. Переводы сохраняют исторический отдел и команду. Изменение прав текущего пользователя не должно автоматически открывать персональные данные бывших сотрудников — требуется отдельная проверка чтения истории и права редактирования.

## Архитектурное решение на согласование

Рекомендуется отдельная история периодов работы сотрудника: employee_id, department_id, team_id, employment_rate и интервал действия. Название таблицы и SQL определяются после проверки живой схемы.

Интервалы в хранении — [начало, конец), без пересечений для одного сотрудника. В UI последняя дата работы включительна. Отсутствующая команда допустима, если это допускает актуальная модель; такой сотрудник не должен исчезать из итогов отдела.

Профиль сохраняется как совместимое представление текущего состояния для существующих модулей. Кадровая операция атомарно обновляет историю и текущее состояние. Для событий будущей датой требуется механизм активации и восстановление после пропуска запуска; нельзя заранее записывать будущий отдел в текущий профиль. Конкретный механизм согласовать после инвентаризации фоновых заданий и импортёров.

Нужно охватить все пути записи кадровых полей, включая админку команд и внешний сервис синхронизации. История, обновляемая только новой формой, будет неполной. Решение о RPC/триггерах принимается после этой инвентаризации.

Увольнение закрывает период и архивирует сотрудника. Полное удаление реального сотрудника с историей должно быть заблокировано на сервере/уровне данных. Закрытие входа и активных сессий — отдельная проверяемая операция; один флаг архива не гарантирует блокировку доступа. Для будущего увольнения доступ закрывается в соответствующий момент, с повторной обработкой ошибок.

## Формулы

- День: сумма ставок загрузок действующего состава / сумма кадровых ставок этого состава × 100%.
- Месяц: сумма дневных загрузок по рабочим дням / сумма дневной ёмкости по тем же рабочим дням × 100%.
- При нулевой ёмкости показывать отсутствие базы расчёта, а не искусственный 0% или Infinity.
- Не усреднять дневные проценты, если ёмкость внутри месяца меняется.
- Гостевые сотрудники не должны удваивать итоги; дефицит и перспективные работы сохраняют действующие правила.
- Существующие фильтры по проекту/сотруднику и статусам загрузок требуют регрессионных проверок, без скрытого изменения семантики.

## Начало учёта и старые периоды — согласовано

Пользователь отказался от восстановления прошлой кадровой истории и согласовал фиксацию исходного состава. Дата запуска T определяется при внедрении по часовому поясу Минска и сохраняется явно; она не вычисляется заново при каждом открытии страницы.

- При запуске один раз сохраняется исходный состав: сотрудники, отделы, команды и ставки. Повторная инициализация не должна перезаписывать этот снимок.
- Для дней до T используется зафиксированный состав, а не текущие поля profiles. Снимок определяет и знаменатель расчёта, и принадлежность сотрудников/загрузок отделам и командам: одной фиксации суммарной ставки недостаточно.
- Для дней начиная с T используются кадровые периоды. У существующих сотрудников начальный период начинается с T; это начало достоверного учёта, а не выдуманная дата приёма. Новые сотрудники учитываются с даты приёма.
- Последующие приёмы, увольнения, переводы и смены ставки не изменяют исходный снимок и не меняют показатели до T. Сотрудников, появившихся после запуска, нельзя автоматически включать в исходный состав.
- Старые месяцы не становятся исторически точными. Восстановление и импорт кадровых событий до T не входят в задачу; старые данные обозначаются как расчёт по составу на дату запуска.
- Фиксируется кадровая база расчёта, а не сами проценты и не loadings. Редактирование прошлых загрузок по-прежнему изменяет соответствующие показатели.
- Месяц, пересекающий T, считается по дням: до T — исходный состав, начиная с T — история. Месячный итог объединяет числитель и знаменатель по тем же рабочим дням, без усреднения процентов двух частей.

Дата создания аккаунта не используется как дата приёма. Подготовка механизма фиксации локально не означает разрешения изменять рабочую БД.

## Этапы

1. Проверка актуальной схемы, RLS, триггеров, потребителей view_employee_workloads, фоновых задач и внешнего импорта. Определить безопасную фиксацию исходного состава и правила доступа к истории; источник прошлых кадровых дат больше не требуется.
2. Аддитивная миграция периодов и защищённые атомарные кадровые операции. План первоначального заполнения, ограничения целостности и проверка обратимости. Подготовка локально; применение только после отдельного подтверждения.
3. Управление приёмом, переводом, ставкой и увольнением в modules/users. Валидация дат, история и понятные конфликты. Сохранить действующие роли и модель полномочий.
4. Серверная выборка истории на просматриваемый диапазон, группировка по историческим командам, дневная ёмкость; обновить DepartmentRow, TeamRow и EmployeeRow. Избегать запросов по одному на день/сотрудника.
5. Инвалидация кэшей и проверка совместимости селекторов, «Занятости», отчётов и фоновой синхронизации. Не открывать исторические данные через клиентскую фильтрацию без серверной проверки.
6. Тесты, ручная приёмка, сравнение расчётов и производительности на репрезентативном диапазоне, документация и review.

## Проверки

- После запуска: 20 полностью загруженных сотрудников в одном месяце; приём 21-го в следующем сохраняет предыдущие 100%.
- До даты запуска: приём, увольнение, перевод и смена ставки после запуска не меняют показатели старых месяцев и распределение старых загрузок по отделам/командам.
- Редактирование самой загрузки до даты запуска изменяет показатель при неизменной кадровой базе.
- Месяц пересекает дату запуска: обе части учитываются без пропусков и двойного учёта; повторная инициализация не перезаписывает исходный состав.
- Замена уволенного новым с согласованными датами; дни разрыва и пересечения занятости.
- Увольнение сохраняет историю и исключает будущую ёмкость; будущие загрузки не удаляются молча.
- Перевод в середине месяца/загрузки: нет потерь и двойного учёта между командами/отделами.
- Ставка 1 → 0,5 влияет только начиная с даты действия.
- Повторный приём, отсутствие команды, пустой отдел, нулевая ёмкость, високосный день и Минск.
- Пересечения периодов и конкурентные кадровые операции отклоняются атомарно.
- Рабочие выходные и праздники одинаково учитываются в числителе и знаменателе.
- Исторические строки отображаются в нужной команде, ключи UI и optimistic updates не смешивают сегменты одного сотрудника.
- Прямые/импортные изменения профиля не обходят историю; архивирование не уничтожает загрузки.
- Уволенный не может продолжить работу через старую сессию после блокировки; ошибки закрытия доступа видимы и повторяемы.

## Ограничения текущего исследования

Внешний сервис Worksection ещё не исследован. Предыдущий категоричный вывод об отсутствии синхронизации кадровых полей не доказан клиентским кодом кнопки: необходимо проверить реализацию отдельного сервиса и его расписание.

## Архитектурное ревью

Pragmatic Architect: направление условно одобрено. Одна таблица периодов и расчёт на диапазон достаточны; универсальная кадровая система не требуется. Перед реализацией зафиксировать источник начальных дат и поддержку будущих кадровых операций. До выбора SQL проверить все пути записи профиля, фоновые задания, серверные права и существующее закрытие доступа. Подготовка миграции не означает разрешение на её применение.

Повторное ревью после согласования исходного снимка: Pragmatic Architect одобрил три узкие сущности (настройки запуска, исходный состав, периоды) с условиями атомарной инициализации, независимости исторического отбора от profiles, защиты обходных записей и проверки импортёра перед включением защиты. Произвольный статус архива не должен дублировать кадровые периоды.

## Технический план хранения — фаза 2.1

Это проект реализации, а не применённая схема. Имена новых сущностей предварительные. Рабочие RLS, функции записи и расписание cron в этом проходе не получены: подключение Supabase запросило повторную авторизацию. После вопроса пользователя повторные подключения прекращены. Прежняя проверка колонок и триггеров остаётся действительной, но не заменяет аудит прав перед внедрением.

### 1. Три сущности с разными обязанностями

| Сущность | Состав | Назначение |
|---|---|---|
| employment_history_settings | Одна запись: cutover_date, initialized_at, initialized_by | Неизменяемая граница T и факт завершённой инициализации |
| employee_employment_baseline | employee_id (уникальный), department_id, team_id, subdivision_id, employment_rate | Неизменяемый исходный состав для дней до T |
| employee_employment_periods | id, employee_id, department_id, team_id, subdivision_id, employment_rate, valid_from, valid_to, created_at/by, updated_at/by | Состав и ставка на каждый день начиная с T |

В снимке и периодах нет зарплат, паролей, ролей и копий профиля. Имена и аватары читаются из сохранённого профиля. Состав для расчёта и группировка не берутся из его текущих кадровых полей. subdivision_id фиксируется для устойчивой группировки подразделений; текущие права зрителя проверяются отдельно.

Отдел и команда могут отсутствовать согласно действующей модели. Сотрудник без команды не должен исчезать из суммы отдела. Служебные профили отделяются от сотрудников при инициализации; последующее изменение признака is_service не должно незаметно менять старую базу. Правила включения и действующие значения NULL/0 у ставок проверяются до запуска, без молчаливого исправления данных. Ставка хранится как numeric; запрета на ставку больше 1 нет: текущий UI допускает 1.25 и 1.5.

Три таблицы выбраны вместо смешивания неизменяемого снимка с редактируемыми периодами или JSON-копии всех профилей. Цена — несколько связей; преимущество — явные ограничения и отдельные права записи. Универсальный журнал кадровых событий не создаётся. Метаданные периодов не обещают полный аудит всех промежуточных исправлений внутри одного дня.

### 2. Ограничения целостности

- Период имеет включительное начало и исключительный конец; NULL в valid_to означает открытый конец. Пустые интервалы запрещены.
- valid_from не раньше T. Операция до T отклоняется; исправление исходной истории не входит в первую версию.
- Периоды одного сотрудника не пересекаются. Предпочтение — ограничение исключения по employee_id и daterange; доступность btree_gist нужно подтвердить до подготовки SQL.
- Транзакции кадровых действий блокируют запись сотрудника и проверяют ожидаемую версию/состояние. Конкурентная устаревшая команда возвращает конфликт, не переписывая результат другой операции.
- Повторное действие с теми же значениями не создаёт период. Несколько изменений в один календарный день меняют состояние этого дня, не создавая пустых интервалов. Более ранние дни и baseline неизменны.
- FK не допускают каскадного удаления снимка и периодов при удалении сотрудника, отдела или команды. Исторические ссылки требуют сохранения сущностей. Переименование не равно изменению исторической принадлежности.
- Нет периода после T — нет кадровой ёмкости. Fallback на текущий profiles запрещён. Несогласованное активное состояние профиля и отсутствие периода отображается как ошибка данных.

Границы и ограничения исключения опираются на [типы диапазонов PostgreSQL](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT).

### 3. Однократный запуск

1. До внедрения сверить список сотрудников, служебные записи, ставки и соответствие отделов/команд. Сравнить текущие суммы с расчётом будущего снимка; ошибочные данные показать, а не менять автоматически.
2. Согласовать точную дату T по Минску и окно запуска. Не датировать начало задним числом при фактическом запуске позже T. Если запуск внутри дня, явно принять, что состав на момент инициализации представляет весь календарный день T; предпочтительно выполнять запуск до кадровых операций этого дня.
3. В одной короткой транзакции исключить конкурентные кадровые изменения (включая INSERT новых профилей и изменение связанной оргструктуры), сохранить settings, baseline и начальные периоды [T, бесконечность). Блокировка только advisory недостаточна для старых прямых writers.
4. Транзакция либо фиксирует все три части, либо полностью откатывается. Повторный запуск возвращает «уже инициализировано» и не меняет T/снимок.
5. До фиксации инициализации используется старый путь чтения; после — новый. Версия ключей кэша меняется, чтобы не показать снимки, собранные прежним алгоритмом.

Не включать сетевые вызовы Auth или импорта внутрь транзакции снимка. Применение схемы и включение учёта — отдельные управляемые действия: нельзя начать собирать периоды до согласованной фиксации базы. После старта откат UI не должен выключать сохранение истории; откат всей модели требует отдельного плана, а не удаления новых таблиц.

### 4. Один путь кадровых изменений

Предлагаются узкие серверные операции приёма, перевода/ставки, увольнения и повторного приёма. Общий внутренний механизм изменяет периоды и текущее представление profiles атомарно; не нужен универсальный конструктор кадровых процессов.

RPC проверяет пользователя, полномочия на конкретное действие и область доступа, дату, принадлежность команды отделу и актуальность исходного состояния. Изменение ставки сохраняет отдельные действующие полномочия; право сменить команду не даёт право менять ставку или переводить в чужой отдел.

Защитный триггер кадровых полей profiles отклоняет прямую запись, противоречащую действующему периоду. Изменения имени и аватара не создают периодов. Обычные клиенты не могут менять baseline/settings или писать periods напрямую. Привилегированные функции получают минимальные EXECUTE-права, безопасный search_path и собственные проверки доступа; клиентский флаг «разрешить обход» не используется. RLS ограничивает чтение исторических строк текущими полномочиями зрителя, а не только фактом входа. Точные политики определяются после проверки рабочей схемы. См. [Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Подтверждённые локальные пути для перевода на операции:

- services/org-data-service.ts: updateUser и создание профиля;
- modules/users/components/user-dialog.tsx и payment-dialog.tsx: кадровые поля и ставка;
- modules/users/admin/components/AssignToTeamModal.tsx: прямой UPDATE team_id;
- app/api/users/create/route.ts: Auth создаёт базовый профиль, затем выполняется UPSERT;
- app/api/admin/delete-user/route.ts: полное удаление; для сотрудника с историей нужна операция увольнения.

Особый случай создания: базовый профиль, автоматически созданный Auth, не считается оформленным сотрудником до успешного приёма. Завершение создания должно согласовать профиль и первый период. Ошибка не оставляет скрытого сотрудника с неполной историей; компенсация Auth и её ошибки обрабатываются отдельно от SQL-транзакции.

Список не считается полным: RPC, внешняя синхронизация и изменения самой оргструктуры ещё требуют проверки. Нельзя включить запрещающий триггер в production до адаптации известных writers и проверки импортёра. Альтернатива — автоматически считать прямые изменения событиями «сегодня» — проще для старых клиентов, но скрывает смысл записи и конфликтует с запланированными периодами; без отдельного согласования её не выбираем.

### 5. Увольнение и будущие даты

Периоды — источник кадровой активности; отдельная таблица архива не требуется. Флаг текущей активности в profiles допустим только как производная проекция для совместимости. Закрытие доступа к приложению не следует автоматически из отсутствия периода и проверяется отдельно.

Вопрос пользователю отправлен: нужны ли заранее запланированные кадровые изменения. Рекомендация для первой версии — оформление изменений текущим днём; это пока не согласованное сокращение функциональности. Если нужны будущие даты, требуется механизм актуализации текущего профиля, повторная обработка пропущенных запусков и восстановление после ошибки. Расписание рабочей БД не проверено, поэтому его наличие не предполагается.

Даже при операциях на сегодня увольнение с последним рабочим днём сегодня закрывает период завтра. Расчёт активности должен определяться датой чтения; селекторы и ограничение входа обязаны корректно обработать эту границу. Ограничение UI текущим днём не снимает эту задачу. Для полноценных будущих переводов понадобится также своевременное обновление текущих кадровых полей и зависимых грантов.

### 6. Чтение и совместимость расчёта

- Сначала получить доступный зрителю состав по baseline/periods и диапазону, затем загрузки этих сотрудников. Текущий фильтр view_employee_workloads.final_department_id/final_team_id нельзя использовать как предварительный фильтр исторической выборки.
- Разделять числитель и знаменатель по одинаковым кадровым границам и рабочим дням. Не разрезать и не менять исходные loadings.
- Нельзя менять общий view без проверки всех потребителей. Предпочтителен специализированный путь чтения вкладки «Отделы», возвращающий необходимые сегменты за диапазон пакетно, без запросов на каждый день.
- Обновление истории инвалидирует данные затронутых отделов, команд и кадровых селекторов. Начало новых суток также учитывается при текущем представлении. Ключи должны разделять диапазон и область доступа и отличаться от прежней версии расчёта.
- Защита старых процентов относится к кадровым изменениям. Самостоятельные изменения загрузок, фильтров или рабочего календаря не являются замороженными данными.

### 7. Граница первого этапа реализации и проверки

Первый этап: подготовить локальную схему settings/baseline/periods, транзакцию инициализации и проверки целостности на изолированной тестовой БД. Без включения защитного триггера на рабочей БД, без переключения пользовательского UI и без изменений loadings. Далее — кадровые операции и адаптация writers, затем чтение графика и запуск после полной проверки.

Планируемые файлы: новая миграция в supabase/migrations (имя через CLI), SQL-тесты в supabase/tests, модульные типы/тесты в modules/users и расчёт в modules/departments-timeline на последующих этапах. types/db.ts регенерируется по реально применённой тестовой схеме, не редактируется вручную. Наличие локальной тестовой БД ещё нужно проверить.

Обязательные проверки хранения: атомарность и повторный запуск; конкурентное создание/перевод во время снимка; неизменность baseline; запрет пересечения периодов и действий до T; два изменения в один день; сохранность истории при увольнении/удалении; новые сотрудники не попадают в baseline; права чтения и записи; отказ прямого обхода; сбой после создания Auth; переход суток. Расчётные проверки: перевод между отделами, смена ставки, месяц на границе T, ручное редактирование старой загрузки, сравнение исходных сумм до и после запуска.

К внедрению нельзя переходить без проверки рабочей RLS, всех writers/импортёра, способа обработки даты увольнения и конкретного плана применения миграции. Это ограничения готовности к запуску, а не разрешение менять рабочую БД сейчас.

### Результат технического ревью

- Pragmatic Architect: модель одобрена с условиями атомарного запуска, неизменности baseline, независимости выборки от текущего профиля и адаптации импортёра до включения guard.
- DB Architect: модель подходит; дополнительно обязательны безопасное завершение создания пользователя после Auth-триггера, сериализация первого периода, сохранение признаков включения в исходный состав и корректная активность после полуночи. Даже без планирования будущих событий увольнение сегодняшним последним днём требует обработки завтрашней границы.
- Это ревью плана, а не проверка реализованного SQL. Рабочие политики и cron по-прежнему не подтверждены в этом проходе.

## Реализованный этап 1: только хранение

Миграция `supabase/migrations/20261124094052_employee_employment_history_storage.sql` создаёт три таблицы, ограничения и функцию `initialize_employee_employment_history(date, uuid)`. Инициализация не вызывается миграцией. Вся запись и чтение для anon/authenticated/service_role закрыты до реализации прикладного доступа. Функция инициализации — SECURITY INVOKER, доступная владельцу, а не клиентский RPC.

Исходный состав включает неслужебные профили, сохраняет их принадлежность и ставку. NULL, нулевые, отрицательные, бесконечные ставки и NaN останавливают инициализацию с ошибкой вместо молчаливой нормализации. До запуска нужно проверить реальные данные. Снимок сначала копируется, затем запечатывается записью настроек, затем создаются начальные периоды — всё в одной транзакции. Исходные таблицы блокируются от конкурентной записи; повторный запуск отклоняется. После ожидания блокировок повторно проверяется минская дата.

Тесты выполнены на отдельном временном экземпляре PostgreSQL 18.7 (`127.0.0.1:55435`), без Docker и без подключения к рабочему Supabase. Зависимые таблицы синтетические, поэтому это доказательство правил хранения, но не совместимости с реальными Auth-триггерами, RLS и импортом. Конфигурация проекта указывает PostgreSQL 17; перед внедрением нужен прогон на соответствующей схеме/версии.

- `employee_employment_history_storage.sql`: 58 проверок, включая атомарность, границы, отсутствие пересечения, неизменяемость, права и запрет устаревшего транзакционного снимка.
- `employee_employment_history_concurrency.py`: 8 проверок двух сессий, включая конкурентные UPDATE/INSERT во время снимка и конфликт периодов. Только стандартная библиотека Python и psql.

Повторный прогон — в НОВОЙ пустой локальной базе с префиксом `enecawork_hr_storage_test_`. Не использовать рабочую базу: SQL-файл создаёт синтетические таблицы зависимостей. Пример для уже запущенного изолированного экземпляра:

```powershell
& 'D:/PostgreSQL/bin/createdb.exe' -h 127.0.0.1 -p 55435 -U hr_storage_test enecawork_hr_storage_test_next
& 'D:/PostgreSQL/bin/psql.exe' -X -w -h 127.0.0.1 -p 55435 -U hr_storage_test -d enecawork_hr_storage_test_next -f supabase/tests/employee_employment_history_storage.sql
python supabase/tests/employee_employment_history_concurrency.py --psql D:/PostgreSQL/bin/psql.exe --port 55435 --user hr_storage_test --database enecawork_hr_storage_test_next
```

SQL-тест откатывает тестовые строки, оставляя пустую схему для теста конкуренции. Последний сохраняет только свои синтетические данные в одноразовой базе. Скрипты не удаляют базы автоматически и не читают .env.

`types/db.ts` пока не регенерирован: штатная команда обращается к рабочему Supabase, а локальный минимальный fixture не является полной схемой приложения. Перезаписывать общий файл типов синтетическими таблицами нельзя. При подготовке прикладных RPC потребуется полная тестовая схема и генерация типов перед подключением TypeScript-кода. На этом этапе TypeScript-код не менялся.

До запуска функции остаются кадровые операции и адаптация writers, чтение графика, интерфейс, совместимость импортёра и финальная проверка прав. Одну миграцию хранения нельзя считать готовой функцией истории. Первоначальный запуск ревью завершился ошибкой сервиса 403; при повторном запуске DB Architect + Security проверил код и не нашёл блокирующих ошибок для закрытого хранилища. По замечанию ревью инициализация явно ограничена READ COMMITTED, тесты REPEATABLE READ и SERIALIZABLE подтверждают отказ. Полная проверка готовности к production этим не заменяется.

## Этап 2: подключение к приложению — план на согласование

Цель — использовать существующие формы и график без отдельного кадрового экрана. Подготовленная первая версия выполняет кадровые изменения текущим минским днём. Произвольные будущие события и повторный приём не реализованы; это отдельное продуктовое решение, не подразумеваемое согласованием даты запуска учёта.

1. **Сохранение сотрудников.** Перевести кадровые поля в существующих user-dialog, payment-dialog, AssignToTeamModal и создание пользователя на один защищённый механизм. RPC закрывает прежний период, создаёт новый и обновляет текущее представление профиля в одной транзакции. Повторная правка текущего дня корректирует этот же день. Имя, аватар и прочие поля остаются в прежнем пути. Проверки прав на организационную структуру и ставку сохраняются отдельно. Guard кадровых полей включается только после адаптации всех writers, включая импорт.
2. **Завершение работы.** Для сотрудника с историей использовать явную команду вместо физического удаления. Последний рабочий день включителен; сегодняшнее увольнение исключает сотрудника из ёмкости с завтра. Выбор сотрудников учитывает период на дату чтения. Вход и активные сессии не блокируются автоматически только фактом закрытия периода: существующий процесс закрытия доступа требует отдельной интеграционной проверки. Загрузки за пределами периода сохраняются; конфликт видим и не маскируется автоматическим удалением.
3. **Чтение графика.** Передать просматриваемый диапазон в getDepartmentsData/useDepartmentsData и ключ кэша; для месячного вида взять полные отображаемые месяцы. Специализированная выборка начинает с baseline/periods, затем получает профили и загрузки, сохраняя серверную область доступа, restricted и гостевые правила. Общий view для других модулей не переписывать. Строки одного сотрудника в разных командах должны иметь устойчивые составные UI-ключи; ID сотрудника и загрузки остаются исходными.
4. **Расчёт.** Добавить дневную кадровую ёмкость в данные сотрудника/команды/отдела и один общий расчёт для дневного и месячного вида. DepartmentRow и TeamRow используют ёмкость соответствующего дня; месячный процент — отношение сумм по одинаковым рабочим дням. Шапка явно показывает текущую ёмкость, не выдавая её за ёмкость всех прошлых дат. Гостевые строки не удваивают итог отдела. Пересечение полосы загрузки с кадровыми периодами меняет отображение/расчёт, но не исходные даты loadings и не данные формы редактирования.
5. **Обновления и проверка.** Расширить существующую инвалидацию кэша на кадровые изменения, смену даты после сна/полуночи и завершение работы; прежний staleTime Infinity не должен навсегда сохранять вчерашнюю активность. Проверить оптимистичные изменения одной загрузки во всех её отображаемых сегментах. Регрессии: новые сотрудники, перевод, смена ставки, завершение работы, отсутствие команды, граница T/месяца, гостевые сотрудники, restricted-проекты и права.

Подтверждённые точки: сейчас getDepartmentsData получает только фильтры; useDepartmentsData использует staleTime Infinity; org-фильтры применяются к final_department_id/final_team_id до сборки сотрудников. DepartmentRow/TeamRow делят загрузку на одну текущую сумму ставок. Именно эти границы необходимо изменить; одной замены формулы недостаточно.

Pragmatic Architect: направление одобрено с условиями дневной точности, обработки увольнения на следующий день, исторического отбора до загрузок и разделения подготовки/включения. Внутридневный аудит и универсальный планировщик не нужны. Рабочая миграция/инициализация не выполняются в рамках планирования.

## Подготовленное подключение (19 ноября 2026)

Добавлена миграция `20261124094101_employee_employment_operations.sql`. Она устанавливает `employee_employment_status`, `update_employee_employment`, `register_employee_employment`, `finish_employee_employment` и guard кадровых полей profiles. Инициализация по-прежнему отдельная. RPC проверяют authenticated actor и динамические права; таблицы истории доступны только серверному чтению, не клиентскому SELECT. Guard начинает проверять соответствие профиля истории после активации.

Все операции этой версии выполняются текущим минским днём. Повторная правка в тот же день корректирует один период. Завершение работы закрывает период завтрашним днём (сегодня включительно), не удаляет профиль/роли/Auth и не изменяет loadings. Полноценное закрытие доступа и повторный приём не добавлены.

Вкладка «Отделы» получает диапазон и строит строки по сохранённой принадлежности, а не текущему отделу профиля. До T действует исходный состав, начиная с T — периоды. Ставка и загрузки агрегируются по одному набору рабочих дней. Исторические полосы визуально ограничены периодами; модалка открывает оригинальную загрузку. Прямое растягивание/разрезание сегментированной полосы отключено. Для просмотра до T показано пояснение о составе на дату запуска.

Чтение истории требует сессии и непустого разрешённого scope. Серверная привилегированная выборка ограничена разрешёнными отделами/командами и гостевыми грантами. Restricted-проекты проверяются авторитетным запросом с отказом при ошибке. Сотрудник со скрытыми загрузками сохраняет штатную ёмкость. Гостевая ёмкость не удваивает итог отдела. Для ограниченного scope загрузки за пределами разрешённых кадровых сегментов не выдаются как «конфликты».

Ключ графика включает диапазон и текущий минский день; периодическое обновление — раз в минуту в активной вкладке, также используется существующая инвалидация профилей/загрузок. Завершение работы инвалидирует локальные списки графика и доски. Публикация закрытой RLS-таблицы periods не используется как ложная гарантия Realtime. Старый prefetch графика без диапазона отключён.

Селекторы новых загрузок используют отдельный датированный список кандидатов. Общий список пользователей сохраняется для подписей старых назначений. До привилегированного чтения периодов сервер проверяет область права назначения, включая разрешённый отдел, команду и гостевые гранты; отсутствие такого права прекращает запрос. Новое назначение требует непрерывного периода работы на весь диапазон; смежные кадровые периоды допустимы. Основные create/reassignment actions и ручное размещение на доске повторяют проверку на сервере. Редактирование прежнего исполнителя не запрещает корректировать старую загрузку; существующие записи не переписываются и не удаляются автоматически. Проверка приложения не заменяет прежние RLS и не является новым глобальным DB-ограничением на все возможные внешние INSERT loadings.

### Проверки и границы готовности

- PostgreSQL 18.7, изолированная база с синтетической схемой: 58 проверок хранения + 49 кадровых операций; 8 ранее выполненных проверок конкуренции хранения.

### Исправление переноса отдела 2026-11-23

`20261124094116_employee_employment_department_transfer.sql` заменяет функцию существующего триггера `sync_employee_subdivision`. Форма и единственный путь UPDATE отдела сохраняются. До активации сохраняется прежняя синхронизация. После активации функция проверяет сессию, существующий профиль и право `users.manage.departments` (как глобальный выбор подразделения в админке); нет нового публичного RPC и клиентских прав записи в историю. Прямая запись кадровых полей по-прежнему защищена guard.

Перенос выполняется в одной транзакции с UPDATE отдела: период текущего дня корректируется, прежний период закрывается и создаётся новый, исходный baseline не меняется. При разделении сохраняется дата окончания, включая последний рабочий день сегодня. Уже завершённые профили/периоды остаются историческими; служебные и ещё не зарегистрированные профили получают только новое подразделение без неявного приёма на работу. Несогласованность хотя бы одного действующего периода отменяет весь перенос.

Для редкого структурного переноса используется `EXCLUSIVE`-блокировка таблицы `profiles`: обычное чтение продолжается, кадровые записи и `SELECT FOR UPDATE` ждут завершения транзакции. Состав и день Минска читаются после получения блокировки; требуется READ COMMITTED. Это сознательный компромисс против пропуска конкурентного приёма/перевода. При смене суток во время обработки операция откатывается с требованием повторить.

Финальный прогон в `enecawork_hr_storage_test_11` (PostgreSQL 18.7): 58 storage + 49 operations + **27** department-transfer assertions, затем **21** проверка двух соединений. Все прошли, включая ожидание коммита нового сотрудника и продолжение того же запроса переноса без retry. Постоянные тесты: `supabase/tests/employee_employment_department_transfer.sql`, `employee_employment_department_transfer_concurrency.py` и fixture рабочих триггеров `fixtures/employment_profile_triggers.sql`. В тестах нет настоящих сотрудников; полная Supabase-схема/RLS/Auth этим не воспроизводится.

Новых подписок/ключей не нужно: существующие изменения profiles/departments инвалидируют timeline, админка также обновляет его после сохранения. Ограничение: фильтр подразделения и доступ руководителей используют текущую принадлежность отдела. Исправление сохраняет периоды и показатели конкретного отдела, но не вводит просмотр исторического состава подразделений или прежние права доступа после переноса.

Рабочая база не изменялась.

### Проверка внешнего синхронизатора 2026-11-23

Через GitHub прочитан `eneca-dev/ws-users-to-work`, commit `fe3afbbbad110e2013114e2c00efaf0c2ebd1b84` (main на момент проверки). Соответствие этой версии текущему серверному deployment ещё не проверено; сервис не запускался и не менялся.

- `sync/user-create.js`: Auth create → profiles upsert → user_roles insert, без регистрации периода. После включения истории такой сотрудник останется без периода; текущий rollback также физически удаляет Auth при ошибке профиля/роли, что нужно учесть при добавлении регистрации.
- `sync/user-delete.js`: soft delete — прямой UPDATE `profiles.department_id/team_id` в отдел/команду «Удалены». Для сотрудника с активной историей новый guard отклонит этот переход. Требуется согласованная с историей обработка выбытия, не отключение guard.
- `sync/user-update.js`: обновляется **salary**, не employment_rate. Эта операция не меняет кадровые поля и сама по себе не блокируется guard.
- `sync/sync-manager.js` вызывает все три пути; `services/scheduler.js` предусматривает автоматические запуски. Поэтому проблема не сводится к ручной кнопке проекта.

Перед активацией нужно адаптировать создание/выбытие в синхронизаторе и проверить совместный сценарий. Текущие authenticated employment RPC требуют auth.uid и не могут считаться готовым интерфейсом фонового service-role импорта. Нужен отдельно ограниченный контракт интеграции с идемпотентностью и сохранением истории. Изменения внешнего репозитория/деплой в этой проверке не выполнялись.

### Реализованная совместимость — только EnecaWork (2026-11-23)

Пользователь запретил менять/обновлять внешний `ws-users-to-work` и согласовал автоматический вариант без ручного подтверждения каждого сотрудника. Подготовлена миграция `20261124094128_employee_employment_legacy_import.sql` внутри EnecaWork. Внешний сервис не менялся и не запускался; рабочая миграция не применялась.

Read-only проверка живого `create_profile_on_signup` подтвердила: Auth INSERT создаёт не только профиль, но и default user_roles. Последний явный INSERT роли старого импортёра поэтому может завершаться duplicate, который импортёр считает успехом. Он проверяет только error, не требует возвращённую строку. Безусловная регистрация при Auth/profile INSERT и регистрация только по успешному AFTER INSERT роли не подходят.

Реализованный автоматический вариант:

1. Ограниченный адаптер завершающего INSERT user_roles только для подтверждённого исходного DB-контекста service_role, нового валидного неслужебного профиля без истории. Не доверять user_metadata, клиентскому флагу или current_user внутри SECURITY DEFINER. Auth-bootstrap не считается завершением импорта.
2. Заблокировать профиль, проверить готовность и зарегистрировать период текущим минским днём в транзакции вставки роли. Если точная пара user_id/role_id уже существует, завершающий системный запрос становится успешным no-op (BEFORE INSERT RETURN NULL), а регистрация сохраняется. При реальной ошибке вставки/валидации история откатывается вместе с этим SQL-запросом. Обычные клиентские назначения ролей не меняются; повторное событие не открывает завершённую историю.
3. Для доверенного системного перевода в настроенную пару UUID отдела/команды «Удалены» закрывать текущий период концом сегодняшнего дня и сохранять прежние оргданные в истории. Разрешить именно этот переход профиля через узкое правило guard; не ослаблять остальные запреты. Повторное выбытие идемпотентно, восстановление не означает автоматического повторного приёма. Пользователь подтвердил: последний рабочий день — сегодня включительно.
4. Системные операции записывают NULL в actor; generated stored поля created_source/updated_source вычисляют system для NULL и user для человеческого actor. Не приписывать импорт владельцу исходного снимка или самому сотруднику. Общий service-role ключ не устанавливает, что источник именно Worksection.
5. Проверить воспроизведённый старый контракт: Auth bootstrap → profile upsert → роль (включая duplicate); отказ до финализации допускает прежний Auth rollback; отказ финального INSERT не оставляет период; повтор/конкуренция не дублируют периоды; переход в «Удалены» сохраняет прошлое; анонимный/пользовательский вызов не получает системного обхода. Код импортёра в production не запускать.

Ограничение: несколько HTTP-вызовов старого сервиса не становятся одной транзакцией. Если финальный SQL уже закоммичен, но ответ потерян, последующее компенсирующее удаление Auth не уничтожает подтверждённую историю; такой сбой потребует сверки результата. Ежедневное ручное подтверждение сотрудников не требуется. Не использовать задержку/таймер или удаление «сегодняшней неиспользованной истории» как эвристику завершения импорта.

Pragmatic review одобрил узкую автоматическую интеграцию. После реализации DB/Security и Cache review не нашли оставшихся блокирующих дефектов в рассмотренном пути. Соответствие найденного main фактически развёрнутой версии импортёра пока не доказано.

Ограничения совместимости:

- Технический профиль после системного архивирования находится в «Удалены», а последний день истории относится к прежнему отделу. Конкретный порядок выпуска:

1. Разработчик проверяет `npm.cmd run build`, ревьюит изменения и подготавливает публикацию согласованного кода через штатный процесс команды. Коммит, push и deployment агентом не выполняются без отдельного поручения. Нельзя публиковать содержимое supabase/.temp или сам бэкап.
2. До изменений рабочей схемы проверить свежую резервную копию/доступную точку восстановления. Бэкап 23 ноября 01:41 проверен локально, но не содержит последующих рабочих изменений. При переносе запуска повторить preflight данных и сверку затрагиваемых функций.
3. По отдельному разрешению применить только четыре миграции этой задачи по порядку, **без вызова initialize**. Не выполнять общий push всех неприменённых миграций репозитория. Этот шаг можно выполнить перед публикацией кода: при отсутствии записи настроек история остаётся выключенной. После каждого файла проверить успешное завершение; транзакция каждого файла не делает весь пакет из четырёх атомарным.
4. Опубликовать обновлённый код, подтвердить успешный production deployment и проверить обычное чтение/кадровое сохранение на тестовом отделе при выключенной истории. Подтвердить контракт фактически развёрнутого внешнего импортёра; просмотренный GitHub main не является доказательством версии deployment.
5. Только после этих проверок отдельно разрешить initialize: указать существующий профиль оператора и фактическую текущую дату Минска. Не закреплять дату 23 ноября заранее. Инициализация действует на всю организацию, не только тестовый отдел.
6. После включения обновить страницы и проверить тестовые приём, ставку, перевод, завершение, обычного руководителя и неизменность прошедших дней. Проверить сохранность loadings и появление новых периодов. Автоматический rollback после активации не подготовлен: не удалять настройки/периоды и не возвращать старые writers вслепую; при ошибке остановить затронутые кадровые записи и исправить причину, сохранив историю.

Ни один из рабочих шагов применения/публикации/активации в ходе read-only сверки не выполнялся.
