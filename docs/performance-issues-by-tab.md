# 1. Общие проблемы (касаются всех вкладок)

## 1.1. Двойная подписка на изменения

**Что не так**
В коде есть компонент `<RealtimeSync />`, который слушает изменения в БД. По ошибке он рендерится **два раза** — один раз в `ClientProviders.tsx`, второй раз внутри `QueryProvider`. Из-за этого каждое событие в БД обрабатывается дважды.

**Почему так получилось**
В `QueryProvider` есть «удобство» — авто-включение realtime по умолчанию. А в `ClientProviders` его рендерят явно. Никто не заметил дубликат, потому что Supabase в браузере создаёт один канал (по имени), но обработчики React навешиваются дважды.

**Под капотом сейчас:**
```
В БД произошло изменение
       │
       ▼
   ┌───────┐
   │ Канал │ ─────────── один канал, ОК
   │ cache-│
   │ sync  │
   └───────┘
       │
       ├──► Обработчик #1 (из QueryProvider) → invalidate кэш
       │
       └──► Обработчик #2 (из ClientProviders) → invalidate кэш ещё раз
```

**Как чинить**
Убрать `<RealtimeSync />` из `query-provider.tsx`, оставить только в `ClientProviders.tsx`. Дополнительно — вынести ссылку на канал на уровень модуля, чтобы был настоящий singleton.

**Эффект**
**−50% лишних реакций** на изменения в БД. **5 минут работы.** Самый дешёвый и самый быстрый фикс.

## 1.3. Слишком широкая инвалидация: одна правка → перерисовываются 3 вкладки

**Что не так**
Когда пользователь меняет одну загрузку, код помечает «устаревшими» **6 разных групп данных** сразу. Если у тебя открыта вкладка «Отделы» и кто-то на «Разделах» двигает загрузку, тебе прилетает событие, и у тебя перезагружается **вся** иерархия отделов.

**Под капотом:**
```
Пользователь двинул ОДНУ загрузку
       │
       ▼
В БД: UPDATE loadings SET start = '2026-06-20' WHERE id = 'X'
       │
       ▼
Realtime канал получает событие
       │
       ▼
Код помечает устаревшими ВСЕ ниже:
  ┌─────────────────────────────────────────┐
  │ ✗ loadings.all                          │
  │ ✗ resourceGraph (включая 'loadings')    │
  │ ✗ departmentsTimeline.all (всё дерево!) │
  │ ✗ sectionsPage.all (всё дерево!)        │
  │ ✗ budgets.calc()                        │
  │ ✗ budgets.calcByDepartments()           │
  └─────────────────────────────────────────┘
       │
       ▼
Эти данные перезагружаются автоматически
→ запрос в БД view_employee_workloads (1 сек)
→ запрос в БД view_departments_sections_loadings (2.5 сек)
→ запрос в БД v_cache_section_calc_budget (1 сек)
→ перерендер деревьев на тысячи DOM-узлов

И это от ОДНОЙ правки одной загрузки.
```

**Самый страшный сценарий:**
Пользователь выделил 50 загрузок и сдвинул их одной кнопкой («bulk shift»). Это **50 отдельных UPDATE** → 50 событий realtime → **до 50 перезагрузок** всего дерева подряд. Браузер начинает «лагать».

**Это объясняет 25 000 вызовов `view_employee_workloads` за неделю** в реальной системе.

**Как чинить**
Использовать данные из самого события: «изменилась загрузка с ID такой-то» → обновить только её в кэше, без перезагрузки всего дерева. Плюс — debounce 500 мс, чтобы при 50 правках подряд была одна перезагрузка, а не 50.

**Эффект**
−70-80% повторных запросов. После bulk-операций браузер перестаёт лагать.

## 1.4. Слишком много таблиц подписано на realtime

**Что не так**
В Supabase в специальный список «publication» добавлено **26 таблиц**. Каждое изменение в каждой из них генерирует событие. Среди них есть таблицы, которые **меняются очень часто** (история прогресса задач, чекпоинты) — каждое изменение пробивается до клиента.

**Какие таблицы в списке (26 штук):**
budgets, chat_messages, checkpoint_audit, checkpoint_section_links, checkpoint_types, clients, decomposition_items, decomposition_stages, department_budget_settings, departments, employee_loading_access_grants, loadings, notifications, objects, profiles, projects, role_permissions, section_checkpoints, **section_readiness_checkpoints**, **section_readiness_snapshots**, sections, stages, teams, user_notifications, user_permissions_cache, user_roles

Особо вредные:
- `section_readiness_snapshots` и `section_readiness_checkpoints` — у этих таблиц ОЧЕНЬ много изменений, и каждое **триггерит полную перезагрузку** `v_resource_graph` (8.5 сек!)
- `user_permissions_cache` — кэш прав, тоже меняется часто
- `role_permissions` — то же

**Под капотом:**
```
Postgres → WAL (журнал изменений) → Supabase Realtime → Все клиенты

   За неделю:
   30 670 WAL events × 7 мс обработка = 212 секунд CPU
   (только на обработку, без бизнес-логики)
```

**Как чинить**
1. Убрать из publication таблицы, которые **не нужны клиенту** в реальном времени (history, snapshots, audit-таблицы).
2. Те, что оставить — должны иметь точечную инвалидацию (см. п. 1.3).

**Эффект**
−30-50% нагрузки на realtime канал. Меньше jank-а в UI при активной правке другими пользователями.

## 1.5. Авторизация дёргается на каждое действие — 190 000 раз в неделю

**Что не так**
Запрос `auth/v1/user` (проверка «кто вы») делается **190 140 раз за 7 дней** — это 29 раз в минуту. На самом деле сессия пользователя меняется раз в час, а проверяется — постоянно.

Дополнительно: `view_user_roles` (роли пользователя) — **p95 = 9.6 секунды**. Это очень медленный запрос, и он делается на каждый чих.

**Как чинить**
Это **отдельная проблема**, которую в моих анализах я **не разбирал глубоко**. Скорее всего, в middleware или провайдере на каждый запрос делается auth-чек заново, вместо использования закэшированной сессии.

**Эффект**
Точно сказать не могу без отдельного анализа, но интуитивно — **на каждой странице −500-1500 мс из общего времени загрузки**.

## 1.6. Тяжёлые SQL view: 4 EXISTS, OR в JOIN, ORDER BY без LIMIT

**Что не так**
Две главные view (`view_employee_workloads` и `view_users`) написаны неоптимально:
- 4 раза делают EXISTS-проверку ролей (admin, department_head, team_lead, user) — могли бы сделать одним JOIN
- Сортируют ВСЕ строки (`ORDER BY`), даже если потом надо вернуть 100
- В `view_employee_workloads` есть OR в JOIN, который **отключает** использование индексов

**Под капотом (`view_employee_workloads`):**
```
На каждую строку результата выполняется:

  ┌─────────────────────────────────────┐
  │ JOIN sections ON                    │
  │   (loading_stage IS NOT NULL        │ ← OR-условие
  │    AND s.id = ds.section_id)        │   ломает индексы
  │   OR                                 │
  │   (loading_stage IS NULL            │
  │    AND s.id = l.loading_section)    │
  └─────────────────────────────────────┘
              │
              ▼ Postgres делает:
  ┌─────────────────────────────────────┐
  │ Bitmap Index Scan idx_sections (1)  │
  │ Bitmap Index Scan idx_sections (2)  │ ← ОДИН индекс
  │ Bitmap Index Scan idx_sections (3)  │   сканится 3 раза!
  │       BitmapOr                       │
  └─────────────────────────────────────┘

  Стоимость: 22 799 buffer hits = 72% всего запроса
```

**Как чинить**
1. Переписать OR в JOIN через UNION ALL (две отдельные ветки вместо одной с OR)
2. 4 EXISTS заменить на один JOIN с агрегацией ролей или сделать materialized view `mat_user_primary_role`
3. Убрать `ORDER BY` из view — пусть клиент сортирует уже на меньшем датасете

**Эффект**
Запрос `view_employee_workloads`: **p95 988 мс → ~200-300 мс** (в 3-5 раз быстрее). С учётом 25k вызовов в неделю — экономия около часа CPU БД в неделю.

## 1.7. Главная справка пользователей вызывается 49 000 раз в неделю

**Что не так**
View `view_users` — это сборная информация о сотрудниках (имя, отдел, команда, должность, роли). За неделю она дёргается **49 070 раз**. Это много.

Источник:
- Каждое создание/изменение загрузки делает дополнительный запрос «посмотреть кто этот пользователь» (`view_users.select('team_id').eq('user_id', X)`) — даже если эти данные уже есть в системе
- Permissions-проверки тоже бьют в эту view

**Под капотом:**
```
Пользователь нажал "Сохранить загрузку"
       │
       ▼
   ┌──────────────────────────────┐
   │ Action: updateSectionLoading │
   └──────────────────────────────┘
       │
       ├──► SELECT * FROM view_users WHERE user_id = ?   ← ЛИШНИЙ
       │    (получить team_id, department_id)               запрос
       │
       ├──► assertCanEditLoading()                       ← ещё запрос
       │    (проверка прав - тоже бьёт view_users)
       │
       └──► UPDATE loadings ...

   На одно сохранение — 2-3 запроса к view_users
```

**Как чинить**
1. `team_id`/`department_id` пользователь уже знает (они есть в фронте). Передавать их прямо в мутацию вместо лукапа.
2. Сделать materialized view `mat_users` — это закэшированная копия таблицы, которая обновляется триггерами. Чтение становится почти мгновенным.

**Эффект**
- Передача `team_id` в мутации → **49 070 → ~5 000 вызовов** в неделю (в 10 раз меньше)
- Materialized view → каждый из оставшихся вызовов в **10-15 раз быстрее**
- Суммарно: экономия **2-3 часов CPU БД в неделю**

## 1.8. На таблице `loadings` 15 индексов, из которых 9 не используются

**Что не так**
На таблице загрузок навешано 15 индексов. Из них:
- **6 действительно используются** (по responsible, section, активные и т.п.)
- **9 — ноль использований** за всё время. Они только тормозят запись.

Каждый раз, когда вы сохраняете загрузку, Postgres обновляет **все 15 индексов**, 9 из которых никому не нужны.

При bulk-операциях это становится заметно: 50 загрузок × 9 ненужных индексов = **450 ненужных обновлений индексов**.

**Какие именно лишние** (полный список в [performance-analysis-tasks-tabs.md](performance-analysis-tasks-tabs.md), раздел 5.4):
- idx_loadings_status, idx_loadings_period, idx_loadings_start, idx_loadings_finish
- idx_loadings_active_date_range, idx_loadings_section_active, idx_loadings_stage_active
- idx_loadings_shortage_flags (× 3 варианта)
- idx_loadings_status_finish_date

**Как чинить**
Удалить эти 9 индексов командой `DROP INDEX` (только после ревью DBA).

**Эффект**
Сохранение загрузок будет в **2-3 раза быстрее**. Размер таблицы уменьшится. Bulk-операции перестанут долго висеть.

⚠️ Это **DDL операция** — только с разрешения, и желательно сначала проверить ещё раз что эти индексы действительно никем не используются.

## 1.9. У 42 связей (foreign key) нет индексов

**Что не так**
В БД 42 связи между таблицами не имеют индексов. Это значит: когда происходит JOIN или удаление родительской записи, Postgres делает **sequential scan** дочерней таблицы.

Самые болезненные:
- `profiles.category_id` — нет индекса → `view_users` делает sequential scan
- `profiles.position_id` — то же
- `profiles.city_id` — то же
- `decomposition_items.responsible` — нет индекса
- `decomposition_items.status_id` — нет индекса
- `decomposition_stages.created_by`, `status_id` — нет индексов
- `loadings.loading_task` — нет индекса
- `teams.department_id` — нет индекса
- `projects.client_id` — нет индекса
- `budgets.created_by` — нет индекса

**Как чинить**
Добавить `CREATE INDEX` для каждой связи. Маленькая операция, большой эффект.

**Эффект**
Просто исчезнут лишние sequential scans. Для каждого JOIN — выигрыш от пары мс до сотен мс в зависимости от размера таблицы.

## 1.10. 5 дубликатов индексов (двойная работа на запись)

**Что не так**
В БД есть 5 пар индексов, которые делают одно и то же. Каждое изменение записи обновляет **оба**, хотя один лишний.

| Таблица | Дубликаты |
|---|---|
| `sections` | `idx_sections_parent_project` ≡ `idx_sections_project_id` |
| `objects` | `idx_objects_object_project_id` ≡ `idx_objects_project_id` |
| `calendar_events` | `calendar_events_calendar_event_id_key` ≡ `pkey` |
| `permissions` | `idx_permissions_name_unique` ≡ `permissions_name_key` |
| `user_roles` | `user_roles_pkey` ≡ `user_roles_user_id_role_id_key` |

**Как чинить**
В каждой паре удалить один индекс. Какой именно — решает DBA.

**Эффект**
Микро-выигрыш на запись. Для записи `sections` (одна из горячих таблиц) ускорение заметно.

## 1.11. Две таблицы (`section_readiness_*`) сканируются полностью — миллионы строк впустую

**Что не так**
Это **главная находка из БД**. Две таблицы:
- `section_readiness_snapshots` — **495 939 sequential scans** (100% sequential, 0 индексных)
- `section_readiness_checkpoints` — **187 408 sequential scans** (100% sequential)

За всё время аптайма — суммарно прочитано **16.9 миллионов строк**.

У них **есть** индексы (например, `idx_readiness_snapshots_section_date`), но они **не подходят** под запрос, который их использует. Этот запрос сидит внутри `v_resource_graph` (в LATERAL подзапросе) и ищет «последний снапшот по дате DESC». Имеющийся индекс по (section_id, date) ASC не годится.

**Под капотом:**
```
v_resource_graph выполняется:
       │
       ▼
   На каждую строку (а их 17 000+):
       │
       ▼
   LATERAL подзапрос:
   ┌───────────────────────────────────────┐
   │ SELECT jsonb_agg(...)                 │
   │ FROM section_readiness_snapshots      │ ← каждый раз
   │ WHERE section_id = ?                  │   sequential scan
   │ ORDER BY snapshot_date DESC           │   всей таблицы
   │ LIMIT 1                               │
   └───────────────────────────────────────┘
```

**Это и есть основной источник p95 = 8.5 секунд для `v_resource_graph`.**

**Как чинить**
Добавить составной индекс с правильной сортировкой:
- `(section_id, snapshot_date DESC)`
- `(section_id, checkpoint_date DESC)`

Тогда Postgres сможет взять «последнюю запись по разделу» одним прыжком в индекс.

**Эффект**
**Запрос `v_resource_graph` с p95 8.5 сек → ~1-2 сек** (в 4-8 раз быстрее). Это вторая по эффективности оптимизация после фейковой пагинации Канбана.

## 1.12. Таблица `budgets` читается через sequential scan на 24 миллиона строк

**Что не так**
В БД 19 строк в таблице `budgets`. Но Postgres за всё время прочитал из неё **24 039 239 строк через sequential scan** (то есть сканировал всю таблицу 1 264 000 раз).

Это значит: какое-то место в SQL view делает `SELECT FROM budgets` без `WHERE`, и Postgres каждый раз пробегает все 19 строк.

Скорее всего, виновник — `v_cache_loading_money` или сам `v_resource_graph` (где LATERAL по `work_logs` тащит за собой budgets).

**Как чинить**
Найти конкретное место (нужен EXPLAIN на prod-объёме) и добавить либо JOIN с фильтром, либо индекс. Возможно, поможет materialized view.

**Эффект**
Зависит от места. Если это используется в v_resource_graph — ускорение совместно с фиксом п. 1.11.

## 1.13. Materialized views почти не используются

**Что не так**
В БД есть только **1 materialized view** (`mat_project_involved_users`). Это «закэшированная копия» таблицы, которая обновляется триггерами и читается мгновенно. Архитектурно прецедент уже есть — паттерн с триггерами отработан.

Однако НЕТ materialized views для самых горячих и самых читаемых данных:
- `view_users` — 49 070 вызовов/нед (в 10-15 раз быстрее с MV)
- `view_organizational_structure` — 21 750 вызовов/нед (10-100 раз быстрее)
- `mat_user_primary_role` — для замены 4 EXISTS в view_users / view_employee_workloads

**Под капотом — что такое MV:**
```
Обычный view:                Materialized view:
─────────────────             ────────────────────
SELECT каждый раз            Данные посчитаны 1 раз
выполняет JOIN-ы,            и сохранены в таблицу.
агрегаты, EXISTS-ы           Чтение = чтение таблицы
                              (мгновенно).
                              Обновление — по триггеру
                              на изменение источников.
```

**Как чинить**
Создать 3 materialized view + триггеры для обновления (по образцу `mat_project_involved_users`).

**Эффект**
- `mat_users`: экономия ~3000 секунд CPU БД в неделю
- `mat_organizational_structure`: ~1400 секунд CPU
- `mat_user_primary_role`: убирает 4 EXISTS из view_employee_workloads и view_users

Это самые большие выигрыши по cumulative time.

## 1.14. RLS-политики на 3 таблицах сделаны неоптимально

**Что не так**
9 RLS-политик на 3 таблицах (dashboard_widgets, department_budget_settings, dim_work_calendar) вычисляют `auth.uid()` **на каждой строке** результата, вместо одного раза для всего запроса.

На наших 4 вкладках это не критично (там RLS чистый), но при большом числе строк в dashboard_widgets/dim_work_calendar — заметно.

**Как чинить**
Обернуть `auth.uid()` в `(SELECT auth.uid())` в каждой политике. Маленькая правка, большой эффект на больших выборках.

**Эффект**
Запросы к этим таблицам станут в разы быстрее. Не критично для 4 главных вкладок, но полезно.

## 1.15. ⚡ КРИТИЧНО: проверка «кто вы» дёргается 190 000 раз в неделю

**Что не так**
Найден корень одной из главных проблем. Запрос `auth/v1/user` (проверка авторизации) делается **190 140 раз за 7 дней** — 29 раз в минуту. Причина — **три места одновременно** проверяют сессию заново вместо использования уже работающей подписки на изменение сессии.

**Под капотом — три места дублируют друг друга:**
```
   Каждый HTTP-запрос на сайт
              │
              ▼
   ┌─────────────────────────────────────────┐
   │ 1. middleware.ts                        │ ← на КАЖДЫЙ запрос
   │    supabase.auth.getUser() ── ~200 мс  │   проверяется заново
   └─────────────────────────────────────────┘
              │
              ▼ (страница загружается)
   ┌─────────────────────────────────────────┐
   │ 2. UserSync.tsx                         │ ← при монтировании
   │    supabase.auth.getUser() ── ~200 мс  │   ещё раз (дубль)
   └─────────────────────────────────────────┘
              │
              ▼ (загрузка permissions)
   ┌─────────────────────────────────────────┐
   │ 3. get-filter-context.ts                │ ← при каждом action
   │    supabase.auth.getUser() ── ~200 мс  │   третий раз
   └─────────────────────────────────────────┘

   Итого: 3 проверки сессии × 200 мс = +600 мс к каждой загрузке.
   
   А `AuthProvider` УЖЕ слушает onAuthStateChange — все 3 вызова лишние!
```

**Как чинить (по приоритету)**

1. **Убрать `getUser()` из middleware** — использовать только cookie-based проверку (middleware framework уже синхронизирует сессию через куки)
2. **Удалить компонент `UserSync.tsx`** — `AuthProvider.onAuthStateChange` уже покрывает все случаи
3. **Кэшировать `getFilterContext` на 5 минут** — context меняется редко, но сейчас дёргается на каждый action

**Эффект**
- **−150 000 запросов в неделю** (~75% всех auth-вызовов)
- **TTFB загрузки `/tasks` уменьшится на 200-500 мс** (убираются 2 лишних блокирующих запроса из критического пути)
- Меньше очередь на connection pool → стабильнее p95 всех остальных запросов

```
Открыли канбан                     Прокрутили вниз
       │                                  │
       ▼                                  ▼
```

## 2.4. Список задач сортируется заново при каждой перерисовке

**Эффект**
Меньше re-renders, безопаснее кэш.

## 2.10. Алгоритм трансформации O(rows × stages × tasks)

`departmentsTimeline.all = ['departments-timeline']` — это самый верхний префикс. Когда мы инвалидируем по нему, перезагружаются **и** список отделов, **и** их «свежесть» (`useTeamsFreshness`), хотя это разные запросы.

**Как чинить**
Заменить `departmentsTimeline.all` на `departmentsTimeline.lists()` в инвалидациях.

**Эффект**
−25% перезагрузок freshness при изменениях загрузок.

---

## 3.5. Двойная перезагрузка после каждой правки

**Что не так**
Когда пользователь меняет даты загрузки (`useUpdateLoadingDates`), происходит **двойной refetch**:
1. Сразу после успеха mutation — код руками вызывает `invalidateKeys: [departmentsTimeline.all, sectionsPage.all]`
2. Сразу же приходит realtime-эхо от изменения `loadings` → опять инвалидация тех же ключей

Итого: одна правка → два повторных запроса к БД.

**Как чинить**
Убрать `departmentsTimeline.all` из `invalidateKeys` mutation — пусть realtime сам инвалидирует. Optimistic update обеспечит мгновенный визуальный отклик.

**Эффект**
−50% запросов на каждую правку.

## 3.6. На сервере делается 100 000 операций с датами на каждый запрос

**Что не так**
Функция `calculateDailyWorkloads` (на сервере) на каждую загрузку перебирает все её дни от start до finish и форматирует дату в строку:

```
for каждой загрузки сотрудника:        ← 5-20 загрузок
  for каждого дня в [start..finish]:   ← 30-90 дней
    formatMinskDate(currentDate)       ← создаёт Date object
    workloads[dateKey] += rate
```

Для 200 сотрудников: 200 × ~500 операций = **~100 000 форматирований даты + map-writes** на каждый запрос.

**Как чинить**
1. Не создавать `Date` объекты — инкрементить строку `YYYY-MM-DD` руками
2. Или перенести агрегацию в БД через `generate_series`
3. Лучший вариант: materialized view `mat_employee_daily_workload`, обновляемый по триггерам

**Эффект**
~~−100-300 мс~~ **−30-80 мс на сервере** (оценка скорректирована: V8 форматирует дату ~3-5 мкс, 100k операций ≈ 30-50 мс реально, не 300). Эффект есть, но не такой большой как изначально оценил.

## 3.7. Та же агрегация делается дважды (по командам и по отделам)

**Что не так**
Функция `aggregateDailyWorkloads` вызывается:
1. Для каждой команды — суммирует daily workloads сотрудников
2. Для каждого отдела — через `.flatMap(team => team.employees)` собирает всех сотрудников и **снова** перебирает их dailyWorkloads

Хотя у нас уже есть посчитанные `team.dailyWorkloads` — можно было бы суммировать их вместо перепрохода по сотрудникам.

**Под капотом:**
```
Сейчас:                            Должно быть:
─────────                          ────────────
Team A: sum(emp1, emp2, emp3)      Team A: sum(emp1, emp2, emp3)
Team B: sum(emp4, emp5)            Team B: sum(emp4, emp5)
Department: sum(                   Department: sum(
  emp1, emp2, emp3,                  Team A,
  emp4, emp5                          Team B
)                                  )

То же значение, но
в 2-3 раза меньше работы.
```

**Как чинить**
Агрегировать отдел через `team.dailyWorkloads`, а не через всех сотрудников заново.

**Эффект**
В сценариях с большими организациями (50 команд × 5 сотрудников × 300 дней) — −50% серверной агрегации.

## 3.8. Нет React.memo на строках таймлайна

**Что не так**
Компоненты `DepartmentRow`, `TeamRow`, `EmployeeRow` не обёрнуты в `React.memo`. При типичной компании на экране 86 400 ячеек (12 отделов × 4 команды × 6 сотрудников × 300 дней). После каждого refetch — полная перерисовка всех ячеек.

## 3.9. Каждая полоска загрузки навешивает свой scroll listener

## 5.6. Правка одного бюджета перезагружает весь расчёт

**Что не так**
Realtime по таблице `budgets` инвалидирует `budgets.all` — а это включает и `useSectionCalcBudgets` (расчёт), хотя `calc` не зависит от таблицы `budgets`.

**Как чинить**
Заменить на точечные ключи: `[lists, details, byEntity, sectionSummary]`, исключив `calc` и `calcByDepartments`.

**Эффект**
Правка суммы бюджета перестаёт тянуть `v_cache_section_calc_budget`.

---

## 5.7. transformProject/Object/Section: миллионы reduce на каждое событие

**Что не так**
Хук `useBudgetsHierarchy` строит иерархию через 5 функций transform. На каждом уровне делается **5 reduce**: plannedHours, loadingHours, calcBudget, loadingCount, errorsCount.

При глубине 5 уровней и 17 000 строк → **миллионы операций синхронно** на каждый refetch. UI замораживается на эти миллисекунды.

**Под капотом:**
```
useMemo (зависит от [projects, budgetsMap, calcMap])
       │
       ▼
   Изменился calcMap → новая Map → пересчёт ВСЕЙ иерархии:
       │
       projects.map(transformProject)
           │
           p1, p2, p3...                ← все 100 проектов
           │
           reduce × 5 metrics            ← на каждом
           │
           transformObject (вложенно)
               │
               reduce × 5 metrics
               │
               transformSection
                   │
                   reduce × 5 metrics
                   ...
```

**Как чинить**
1. Перенести агрегацию в SQL view через `SUM() OVER (PARTITION BY object_id)` — клиент получает посчитанное
2. Или мемоизировать узлы через WeakMap по (node.id, budgetsMap.get, calcMap.get)

**Эффект**
JS time на main thread: ~150 мс → ~5 мс. UI перестаёт лагать.

---

## 5.8. BudgetRow в memo, но expanded ломает memo

**Что не так**
`BudgetRow` обёрнут в `React.memo` — это хорошо. **НО** в props передаётся `expanded: ExpandedState` (объект целиком). При разворачивании любого узла этот объект меняется → меняется ссылка → memo не работает → **все BudgetRow перерисовываются**.

**Как чинить**
Передавать `isExpanded: boolean` (вычислять снаружи), а не весь объект. Колбэки `onToggle`/`onExpandAll` — через `useCallback` с пустыми deps.

**Эффект**
При разворачивании одной строки перерисовывается одна строка вместо 17 000.

---

## 5.9. distributedBudget пересчитывается на каждом рендере

**Что не так**
В `BudgetRow.tsx:86-88`:
```
distributedBudget = node.children.reduce(child.budgets.reduce(...))
```

Это O(grandchildren) на каждом рендере каждой строки. Без useMemo.

**Как чинить**
Перенести в transform (один раз на пересчёт иерархии) или обернуть в useMemo.

**Эффект**
Убирает квадратичную сложность из render-функции.

---

## 5.10. Виртуализации нет — «Развернуть всё» вешает страницу

**Что не так**
При нажатии «Развернуть всё» состояние `expanded` становится Record со всеми 17 000 узлов → все они рендерятся в DOM → **синхронный freeze на секунды**.

**Как чинить**
Flatten иерархии в плоский массив видимых узлов (с учётом expanded) → `@tanstack/react-virtual` с `estimatedSize=32`. Или `react-window`.

**Эффект**
«Развернуть всё» перестаёт вешать страницу. INP падает на порядок.

---

## 5.11. setTimeout не очищается при размонтировании (утечка)

**Что не так**
В `BudgetsHierarchy.tsx:73-77` есть `setTimeout` на 300 мс для скролла к нужной секции при автораскрытии. При быстром переключении табов (Канбан → Бюджеты → Канбан) этот timeout висит и срабатывает после размонтирования компонента → warning «Can't perform state update on unmounted component».

**Как чинить**
Сохранять id таймера и очищать в return cleanup useEffect.

**Эффект**
Устраняет warnings и потенциальные баги при быстром переключении вкладок.

---

## 5.12. Утечка при асинхронной загрузке (prefetch)

**Что не так**
В `usePrefetchSectionsBatch.ts` (используется в resource-graph для прелоад бюджетов) есть цепочка `setTimeout → requestIdleCallback → Promise.all`. При смене проектов во время prefetch старый batch loop продолжает работать в фоне. Также `cancelIdleCallbackPolyfill` некорректно типизирован.

**Как чинить**
Сохранять все pending timer ids в массив, очищать все при cleanup. Исправить типы.

**Эффект**
Корректная отмена prefetch при unmount → меньше памяти, нет race conditions.

# 7. Дополнительные утечки памяти (нашли при углублённом анализе)

## 7.1. ⚠️ HIGH: Listeners на document могут накапливаться (Разделы)

**Что не так**
В `AggregatedBarsOverlay.tsx:205-206` функция `handleResizeStart` (resize загрузки drag-ом) **навешивает listeners напрямую на document** вне `useEffect`. Если пользователь начал resize → компонент размонтировался (например, realtime invalidation перерисовала родителя) — `handleMouseUp` никогда не вызовется → **listeners остаются на document навсегда**.

**Под капотом:**
```
Пользователь начал resize загрузки
       │
       ▼
   document.addEventListener('mousemove', ...) ← навешивается
   document.addEventListener('mouseup', ...)
       │
       ▼
Realtime пришло событие → родитель перерисовался → компонент размонтировался
       │
       ▼
   ✗ handleMouseUp НЕ вызвался
   ✗ removeEventListener НЕ вызвался
       │
       ▼
   Listeners остались на document навсегда
   
   За активную сессию: 50+ листенеров на document → лагает скролл, мышь
```

**Как чинить**
Перенести логику в `useEffect` с правильным cleanup при unmount компонента.

**Эффект**
Устраняет накопление сотен listeners за длинную сессию. Браузер перестаёт «лагать» к концу рабочего дня.

---

## 7.2. Race condition в timeline resize (Отделы)

**Что не так**
В `useTimelineResize.ts:241-256` listeners для resize правильно очищаются, но `handleMouseMove` и `handleMouseUp` находятся в зависимостях useEffect, при этом они **пересоздаются на каждом рендере** (не обёрнуты в `useCallback`). Это значит: каждый рендер пересоздаёт пару listeners. Также есть race condition при быстром unmount во время resize.

**Как чинить**
Обернуть `handleMouseMove`/`handleMouseUp` в `useCallback` с правильными зависимостями. Или использовать ref-pattern.

**Эффект**
Меньше пересозданий listeners → плавнее интерактив. Устраняет race condition.

# 9. Code Quality (рефакторинг, не оптимизация)

Эти пункты раньше были в списке проблем производительности, но при критическом пересмотре оказалось — **они не дают ощутимого ускорения**. Это улучшения качества кода, архитектуры или консистентности. Полезные, но не входят в performance-фиксы.

## 9.1. Голый useQuery в `useSectionCalcBudgets` (Бюджеты)

**Стилистическое нарушение.** Хук написан через прямой `useQuery`, минуя фабрику `createCacheQuery`. Все остальные хуки в проекте используют фабрику. Realtime работает, retry работает (через дефолты `useQuery`), кэш работает. Разница только в консистентности кода.

**Усилия:** 15 мин. **Эффект на производительность:** 0.

## 9.2. Дубль кода `getKanbanSections` ≡ `getKanbanSectionsPaginated`

**240 строк дублированного кода.** Первая функция нигде не используется (только импортируется через index, но не вызывается на странице). Можно безопасно удалить, общий код фильтров вынести в helper.

**Усилия:** 1 ч. **Эффект на производительность:** ~5 KB сжатого bundle (незаметно).

**Две версии одного компонента.** Одна на `/tasks`, другая на `/kanban`. Логика DnD, infinite-load — продублированы (200 строк). Можно объединить через проп `showFilterBar`.

**Усилия:** 1 ч. **Эффект на производительность:** ~5 KB сжатого bundle (незаметно).

---

## 9.4. Layout dashboard весь клиентский

**Архитектурная чистота.** `app/(dashboard)/layout.tsx` сделан `'use client'` из-за Zustand-хуков (sidebar/user store). Это превращает все дочерние компоненты в client. Можно разделить:
- `layout.tsx` — Server (просто обёртка)
- `DashboardLayoutClient.tsx` — Client (хуки sidebar/user)

**Усилия:** 1 ч. **Эффект на производительность:** Нулевой — данные всё равно тянутся через TanStack Query на клиенте, server-side fetching не используется. Это рефакторинг для архитектурной чистоты.
