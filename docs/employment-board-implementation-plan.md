# Доска занятости отдела — план реализации

## 1. Цель

Новая вкладка на странице «Задачи» (`/tasks`), где начальник отдела видит все активные проекты отдела и всех сотрудников отдела на одном экране, и визуально понимает, кто чем занят. Проекты и сотрудники размещаются на доске автоматически на основе текущих загрузок; вручную можно закрепить проект без загрузок и перетащить сотрудника на карточку проекта.

## 2. Схема БД

Изменений в существующих таблицах не требуется. Источники на чтение:

| Источник | Назначение |
|---|---|
| `view_departments_sections_loadings` | активные проекты отдела (есть текущая загрузка сотрудника отдела) |
| `view_users` / `view_organizational_structure` | полный список сотрудников отдела |

Требуются две новые таблицы — только для ручных действий (закрепление проекта, ручное размещение сотрудника). Автоматическое размещение по загрузкам они не хранят и не дублируют.

### `department_pinned_projects`

Проекты, закреплённые на доске вручную (у проекта пока нет активных загрузок сотрудников отдела, поэтому он не появляется на доске автоматически).

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | uuid, PK | идентификатор записи |
| `department_id` | uuid, FK → `departments.department_id` | отдел, на чьей доске закреплён проект |
| `project_id` | uuid, FK → `projects.project_id` | закреплённый проект |
| `pinned_by` | uuid, FK → `profiles.user_id` | кто закрепил — для аудита |
| `pinned_at` | timestamptz | когда закреплён |

`UNIQUE (department_id, project_id)` — исключает дубли закрепления одного проекта.

### `department_board_placements`

Ручные размещения сотрудника на карточке проекта — исключение для случаев, когда формальной загрузки в системе планирования ещё нет.

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | uuid, PK | идентификатор записи |
| `department_id` | uuid, FK → `departments.department_id` | контекст доски |
| `project_id` | uuid, FK → `projects.project_id` | на какой проект помещён сотрудник |
| `employee_id` | uuid, FK → `profiles.user_id` | какой сотрудник размещён |
| `placed_by` | uuid, FK → `profiles.user_id` | кто перетащил — для аудита |
| `placed_at` | timestamptz | когда размещён |

`UNIQUE (department_id, project_id, employee_id)` — исключает повторное размещение одного и того же сотрудника на одном проекте.

Обе таблицы создаются с включённым RLS и политикой доступа по отделу (аналогично остальным таблицам с ограничением по отделу в проекте).

## 4. Страница

Отдельного роута нет — новый вид вкладки на существующей странице `/tasks`, рядом с «Канбан», «Отделы», «Разделы», «Бюджеты» (создаётся и переключается через тот же `TabPicker`/`TabModal`, что и остальные вкладки).

### Разметка

Двухзонный layout внутри вкладки:

- **Основная область (слева, большая часть ширины)** — карточки проектов.
- **Правая панель (фиксированная ширина, sticky)** — источник для перетаскивания, два блока:
  - **Проекты** — все активные проекты отдела (из загрузок) + поиск/добавление любого проекта отдела вручную.
  - **Сотрудники отдела** — полный список, включая тех, кто пока нигде не размещён.

### Принцип размещения карточек

- Карточки проектов заполняют основную область через CSS multi-column masonry (`columns`, `break-inside: avoid`) — карточки естественным образом перетекают по колонкам без пересечений, независимо от их количества и высоты.
- Число колонок адаптируется под ширину экрана.
- Размер шрифта и отступы внутри карточки регулируются CSS Container Queries на уровне самой карточки — зависят от фактического наполнения (числа сотрудников на ней), а не от общего числа карточек на странице.
- Список сотрудников внутри карточки — flex-wrap, карточка растёт по высоте по мере добавления сотрудников.

### Drag-and-drop

- Перетаскивание проекта из правой панели на пустое место основной области → создаёт закреплённую карточку (`department_pinned_projects`).
- Перетаскивание сотрудника из правой панели на карточку проекта → создаёт ручное размещение (`department_board_placements`), сотрудник отображается под проектом.
- Сотрудник, у которого уже есть активная загрузка на проект, отображается на карточке автоматически, без какого-либо перетаскивания (источник — `view_departments_sections_loadings`), визуально отмечен как «по загрузке».
- Сотрудник без загрузок и без ручного размещения остаётся в правой панели с визуальным акцентом — это и есть индикация незанятости.
- Реализация — нативный HTML5 Drag & Drop API по паттерну `modules/kanban` (без `@dnd-kit`, без новых зависимостей).

## 5. Технологии

CSS multi-column + Container Queries для раскладки, нативный HTML5 DnD — по существующим паттернам проекта, без новых зависимостей. Данные — TanStack Query / Server Actions через `modules/cache`, дополненные слоем Redis (см. раздел 6).

## 6. Redis

Осознанное решение — использовать Redis на этой странице, чтобы освоить технологию. Redis — только кэш и вспомогательный слой поверх Postgres, не источник истины: все данные (проекты, размещения, закрепления) остаются в Postgres, Redis можно потерять целиком без потери данных.

### 6.1 Провайдер и регистрация

Managed **Upstash Redis** — единственный практичный вариант под serverless Next.js (Vercel-style): REST-клиент без постоянного TCP-соединения, не упирается в лимит подключений serverless-функций (в отличие от классического `ioredis` + persistent connection). Есть бесплатный tier.

Регистрация — только руками пользователя, я не могу создать аккаунт за вас:
1. Завести аккаунт на upstash.com, создать Redis-базу.
2. Взять `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN` из дашборда.
3. Положить как env-переменные (`.env.local` локально, Vercel env в проде).

Новые npm-пакеты (осознанное исключение из правила «не ставить новые зависимости» — по явному решению освоить Redis): `@upstash/redis`, `@upstash/ratelimit`.

### 6.2 Cache-aside для чтения доски

- Ключ `employment-board:{departmentId}`.
- `getDepartmentEmploymentBoard`: сперва `redis.get(key)`; если пусто — собирает данные из Postgres (view + pinned + placements), пишет `redis.set(key, data, { ex: 60 })`.
- Любая запись (`pinProject`/`unpinProject`/`placeEmployee`/`removePlacement`) сразу делает `redis.del(key)`.
- Даёт: GET/SET/EX, паттерн cache-aside, инвалидация по записи.

### 6.3 Distributed lock на размещение сотрудника

- `placeEmployee(departmentId, projectId, employeeId)` сначала берёт `redis.set(lockKey, 1, { nx: true, px: 3000 })`, `lockKey = lock:placement:{departmentId}:{employeeId}`.
- Если лок уже занят — значит сотрудника прямо сейчас перетаскивает кто-то другой, action возвращает конфликт, UI показывает «уже перемещается».
- Снимается `redis.del(lockKey)` в `finally`.
- Даёт: атомарный `SET NX PX`, паттерн distributed lock, защита от гонки при параллельном drag двух пользователей.

### 6.4 Rate limiting на запись

- `@upstash/ratelimit`, sliding window (например 20 действий / 10 сек на пользователя), проверка перед `pinProject`/`placeEmployee`.
- Даёт: готовый sliding-window limiter поверх Redis, применимый потом и к другим action'ам проекта.

### 6.5 Presence — кто сейчас смотрит доску

- Ключ `presence:{departmentId}:{userId}`, `redis.set(key, timestamp, { ex: 15 })`, обновляется heartbeat-запросом с клиента каждые ~10 сек, пока вкладка открыта.
- Чтение — `SCAN` по `presence:{departmentId}:*` → список активных зрителей, аватарки «сейчас смотрят N».
- Даёт: TTL-ключи как presence-паттерн, `SCAN` вместо блокирующего `KEYS`.

### 6.6 Что сознательно не берём — Pub/Sub

Классический Redis Pub/Sub для живой трансляции в браузер сюда не ложится архитектурно: приложение — serverless-функции (Vercel-style), нет долгоживущего процесса, который держал бы subscribe-соединение и релеил события в WebSocket клиентам. Для живых обновлений в проекте уже используется Supabase Realtime (весь `modules/cache`, `departments-timeline` и т.д.) — дублировать эту роль Redis'ом не нужно. Pub/Sub можно освоить отдельно, если/когда в проекте появится выделенный realtime-сервис.
