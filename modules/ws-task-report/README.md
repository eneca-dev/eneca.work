# Модуль ws-task-report

Отчёт по задачам 3-го уровня Worksection. Отдельная страница `/ws-report`,
пункт в сайдбаре, доступный персональному списку пользователей.

## Ключевая особенность

**Ни одна колонка отчёта не берётся из нашей базы.** Все значения приходят из
Worksection отдельной синхронизацией в таблицу `ws_task_report`. Приложение только
читает эту таблицу и о существовании синхронизации не знает — межсервисных вызовов
и кнопки «Обновить» здесь нет.

Причина: цифры должны совпадать с первоисточником. Если дополнять их данными из
нашей модели, отчёт разъедется с тем, что видно в Worksection.

## Структура

```
modules/ws-task-report/
├── actions/index.ts              # getWsTaskReport, hasWsReportAccess, exportWsTaskReport
├── hooks/index.ts                # useWsTaskReport, useWsReportAccess
├── components/
│   ├── WsTaskReportView.tsx      # фильтры, дата обновления, кнопка выгрузки
│   └── ReportTable.tsx           # 9 колонок, сортировка, итоги
├── utils/
│   ├── sort.ts                   # компаратор — общий для таблицы и выгрузки
│   └── build-workbook.ts         # сборка книги Excel (только сервер)
├── types/index.ts
└── index.ts                      # публичный API
```

## Колонки

| Колонка | Поле | Источник в Worksection |
|---|---|---|
| Объект | `ws_project_name` | проект Worksection — в его названии и шифр |
| Подэтап | `ws_object_name` | задача 1-го уровня (для OS-проектов — имя проекта) |
| Задача | `ws_task_name` | задача 3-го уровня |
| Открыта | `date_added` | `date_added` |
| Статус | `ws_status` | `status`: `active` / `done` |
| Закрыта | `date_closed` | `date_closed` из `get_costs` |
| Часы | `total_hours` | Σ `cost.time` |
| План. бюджет | `planned_budget` | `max_money` → показывается как **есть / нет**, не суммой |
| Сумма, BYN | `total_money` | Σ `cost.money` — уже по ставке исполнителя |

Суммы в BYN — с копейками (`315,84`), часы — с одним знаком (`14,0`). Ноль и
пустое значение показываются прочерком, а не `0,00`, чтобы строки без списаний
не шумели.

Итоговая строка: сумма часов, сумма BYN и счётчик задач с плановым бюджетом
(суммировать его смысла нет, колонка показывает признак).

### Сортировка

По клику на заголовок, направление переключается повторным кликом.

> **Состояние сортировки живёт в `WsTaskReportView`, а не в таблице.** Это
> сделано ради выгрузки: кнопка Excel находится в шапке и должна отдавать файл
> в том же порядке, что на экране. Компаратор вынесен в `utils/sort.ts` —
> модуль без `'use client'` и `'use server'`, поэтому клиент и сервер сортируют
> одинаково.

Колонка планового бюджета сортируется по признаку «есть / нет», а не по величине —
иначе порядок выглядел бы произвольным. Сортировка по объекту вторично группирует
по подэтапу, иначе строки одного объекта перемешались бы.

## Доступ

Персональный список, **не роль**: право нужно конкретным людям, роль-однодневка
была бы лишней сущностью.

```sql
insert into ws_task_report_access (user_id) values ('<uuid>');
```

Четыре барьера:

1. **Middleware** — `/ws-report` не в `publicRoutes`, неавторизованного редиректит на логин
2. **RLS** на `ws_task_report` — проверяет наличие `auth.uid()` в `ws_task_report_access`
3. **Server Action** — явная проверка, чтобы отдать «Нет доступа» вместо пустого списка
4. **UI** — пункт сайдбара скрыт через `useWsReportAccess()`

Проверку делает приватная `checkAccess(supabase, userId)`, принимающая **уже
полученного** пользователя: `auth.getUser()` — сетевой вызов к Supabase, и вызывать
его дважды за одно действие незачем.

Все три Server Action проверяют доступ самостоятельно — их можно вызвать напрямую
по ID, минуя интерфейс.

Политика на самой `ws_task_report_access` разрешает видеть только свою строку.
Поэтому подзапрос в политике отчёта работает без `SECURITY DEFINER`, а список тех,
у кого есть доступ, наружу не утекает.

Добавить человека = один `insert`, без деплоя.

## API

```ts
import { useWsTaskReport, useWsReportAccess } from '@/modules/ws-task-report'

const { data: hasAccess } = useWsReportAccess()

const { data, isLoading, error } = useWsTaskReport(
  { search: 'корректировк', status: 'active' },
  { enabled: hasAccess === true }
)

data.rows          // WsTaskReportRow[]
data.lastSyncedAt  // max(synced_at) по всей таблице
data.total         // сколько строк после фильтров
```

Фильтры: поиск подстрокой по названию задачи (спецсимволы `%` и `_` экранируются,
поэтому «100%» ищется как текст), статус, диапазон даты открытия.

Границы диапазона задаются явно в минском поясе (`+03:00`), чтобы выбранный день
попадал целиком: `gte YYYY-MM-DDT00:00:00+03:00` и `lte YYYY-MM-DDT23:59:59.999+03:00`.

`lastSyncedAt` считается по всей таблице, а не по отфильтрованной выборке — иначе
при пустом результате поиска дата обновления пропадала бы. Под этот запрос есть
индекс `ws_task_report_synced_at_idx (synced_at desc)` — он выполняется на каждую
смену фильтра, и без индекса шёл бы полным сканированием.

## Выгрузка в Excel

Кнопка в правом верхнем углу. Файл повторяет экран: те же фильтры, тот же порядок
строк, те же 9 колонок и итоговая строка.

```ts
import { exportWsTaskReport } from '@/modules/ws-task-report'

const result = await exportWsTaskReport(filters, { field: 'date_added', direction: 'desc' })
// result.data: { fileName, base64, rows }
```

**Книга собирается на сервере.** `exceljs` весит около мегабайта — на клиенте он
раздул бы бандл страницы. Наружу отдаётся base64, клиент собирает `Blob` и отдаёт
браузеру на скачивание.

Что в файле:

- шапка над таблицей: дата синхронизации и словесное описание применённых фильтров
- закреплённые первые строки и автофильтр по заголовкам
- **даты и числа — настоящими типами Excel**, а не текстом, поэтому сортируются
  и считаются на месте
- даты сдвинуты в минский пояс: Excel хранит их без зоны, и без сдвига задача,
  открытая ночью, уехала бы во вчерашний день
- имя файла `otchet-po-zadacham_YYYY-MM-DD.xlsx`

## Синхронизация

Живёт в отдельном приложении: `d:\ws-to-work\task-report\`.

- **Запуск:** собственного расписания нет — отчёт синхронизируется **следом за
  основной синхронизацией**, через хук `onSyncFinished`. Накладок не бывает
  по построению, а не по удачно подобранному времени: обе синхронизации бьют
  один и тот же Worksection API и идут строго друг за другом.
  Основная ходит в 0:00, 3:00, 6:00, 9:00, 12:00, 15:00, 18:00, 21:00 по будням
  (в выходные только в 6:00) — столько же раз отработает и отчёт
- **Отдел зафиксирован в коде:** `REPORT_DEPARTMENTS = Object.freeze(['КР гражд'])`
  в `task-report/departments.js`. Ни env, ни параметр запроса на это не влияют
- **Ручной запуск:** кнопка на `http://localhost:3004`
- **Эндпоинт** отвечает сразу (202), работа идёт в фоне — соединение не висит
  и не рвётся по таймауту nginx

Задачи без ответственного в Worksection не синхронизируются.

## Интеграция

Отдельная страница `/ws-report`, пункт в сайдбаре под «Заметками». Две аддитивные правки:

| Файл | Что |
|---|---|
| `app/(dashboard)/ws-report/page.tsx` | новая страница (новый файл) |
| `components/sidebar.tsx` | пункт меню, скрытый через `useWsReportAccess()` |

Гейт в сайдбаре сделан тем же приёмом, что и «Аналитика» — условный блок вокруг
`<Link>`. Страница `/ws-report` при этом остаётся защищённой сама по себе: если
открыть её по прямой ссылке без доступа, `WsTaskReportView` покажет «Нет доступа»,
а RLS не отдаст ни строки.

Модуль `tasks` не затронут вообще — отчёт живёт отдельно от вкладок Канбан /
Отделы / Разделы / Бюджеты.

## Известные ограничения

- **Закрытые задачи без даты закрытия** (~11%). `date_closed` приходит только внутри
  `get_costs`, поэтому у задач без единого отчёта даты нет. Статус при этом корректный,
  в колонке «Закрыта» стоит прочерк
- **Потолок выборки** 5000 строк. Отдел «КР гражд» даёт ~1900, запас трёхкратный.
  Выгрузка в Excel упирается в тот же потолок
- **Сортировка и итоги считаются на клиенте** — при таком объёме это дешевле, чем
  гонять запрос на каждый клик по заголовку
- **`exceljs` тяжёлый для сборки.** Попав в webpack-бандл, он раздувает кэш сборки,
  и на dev-сервере с накопленной памятью `PackFileCacheStrategy` падает с
  `RangeError: Array buffer allocation failed`. Проблема только на этапе сборки —
  собранное приложение webpack не использует и упасть от этого не может.
  Если всплывёт снова, лечится `serverExternalPackages: ['exceljs']` в
  `next.config.mjs`: библиотека перестаёт бандлиться и подхватывается Node
  из `node_modules` в рантайме
- **`utils/build-workbook.ts` не помечен как серверный.** Сейчас он попадает только
  в серверный бандл, потому что импортируется из `'use server'`-файла, но защиты
  от случайного импорта с клиента нет — пакета `server-only` в проекте нет
