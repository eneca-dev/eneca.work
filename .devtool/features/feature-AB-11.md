# feature-AB-11 Месячный вид на странице «Разделы»

## Зачем

Недельный режим (AB-04) уже покрывает 2 года — `WEEKLY_WEEKS_BEFORE/AFTER = 52/52`. То есть месяц нужен **не ради горизонта**, а ради двух других вещей:

1. **Плотность.** 104 колонки × 50px = 5200px против 15 колонок × 140px = 2100px. Год целиком влезает на широкий монитор без горизонтального скролла — провал в загрузке ловится глазом, а не прокруткой.
2. **Ввод ёмкости.** Проставить плановую ёмкость на полгода вперёд сейчас — 26 кликов по неделям. В месяце — один клик или один drag.

Заказчики и их вопросы:
- **Начальник отдела** — «где у отдела дыры и пики загрузки на горизонте полугода-года», «кого можно отдать на новый проект», «когда придётся нанимать».
- **ГИП** — «обеспечены ли разделы моего проекта ресурсом по месяцам», «в каком месяце пиковая потребность».

На этом горизонте вопрос — «хватает или не хватает и где именно провал», а не «кто в какой день». Точная дата там не нужна: данных такой точности не существует, планы всё равно поедут.

## Решения (согласованы с постановщиком)

1. Заказчик — начальник отдела и ГИП (см. выше).
2. Внутримесячную неравномерность **не показываем** — один агрегированный бар на месяц, как в неделях. (Обсуждалось: месячное среднее скрывает случай «2 человека первые две недели, 0 — последние две» → показывает ровные 100%. Осознанно принято.)
3. Число в ячейке — **среднедневная ставка**, та же формула, что в недельном режиме. Тултип — как в неделе.
4. Строка сотрудника — **полоски загрузок** (`MonthlyLoadingBars`), высота строк по тому же правилу, что в дневном режиме, без клампов.
5. Горизонт по умолчанию — **3 месяца назад + 12 вперёд**, с тем же календариком выбора периода, что в недельном режиме (окно snap-ится к границам месяцев).
6. Ёмкость: клик/drag по месяцам **молча перезатирает** дневные и недельные значения внутри диапазона. Drag за боковые маркеры **остаётся**.

## Проверено в коде до начала работы

**Высота строк сотрудника (решение 4) получается сама.** Дневной режим (`loading-bars-utils.ts:177-193`) даёт бару слой = max(слой пересекающихся по пикселям) + 1; недельный/месячный (`WeeklyLoadingBars.tsx:124-141`) — первый свободный ряд. Правило одно: этажей столько, сколько загрузок пересекается **по датам**, масштаб на это не влияет. При этом месячный бар 24px против дневного 32px и без комментариев → месячная строка при той же глубине **ниже** дневной. Клампить нечего.

**Производительности проблемы нет.** При горизонте 15 месяцев агрегация обходит ~315 рабочих дат; нынешний недельный режим (104 недели) — ~520. Месяц дешевле уже работающего недельного.

**Реальный риск — объём upsert-а ёмкости.** `upsertSectionCapacityBatch` (`actions/index.ts:812`) шлёт все строки одним запросом без разбиения и возвращает их же через `.select()`. Клик по месяцу на проекте из 12 разделов = ~370 строк; drag на 12 месяцев = ~4500 строк в одном server action. Близко к лимиту тела (1MB) и заметно по отклику. Решается чанкованием (этап 6).

## Переиспользуется как есть

- `ScaleToggle` — тип уже `'day' | 'week' | 'month'`, нужно только передать третий режим в `modes`.
- `MonthlyLoadingBars` + `calculateMonthlyBarsRowHeight` + `LoadingBarButton` (sticky-подписи из AB-08) — generic, к «Отделам» не привязаны.
- `useSectionsPageUIStore.timelineScale` — уже типизирован через `TimelineScaleMode`, значение `'month'` переживает persist без миграции.
- Сохранение ёмкости — тот же контракт `onSaveCapacity(startDate, endDate, value)` + `expandDateRange`; обработчики в `ProjectRow`/`ObjectSectionRow` не меняются.
- `flattenSections`, сортировка по актуальности, бейдж «занято X из Y» — завязаны на `customDateRange` и «сегодня», от масштаба не зависят.

### Этап 1. Данные и константы

**`modules/resource-graph/constants/index.ts`**
```ts
export const SECTIONS_MONTH_CELL_WIDTH = 140       // у «Отделов» 200 — там 72 месяца и другой макет
export const MONTHLY_MONTHS_BEFORE_SECTIONS = 3
export const MONTHLY_MONTHS_AFTER_SECTIONS = 12
```

**`modules/resource-graph/utils/monthly-cell-utils.ts`**
1. `MonthCell` — добавить поле `workingDates: string[]` (список дат рабочих дней месяца). Вся агрегация X/Y построена на списке дат, а не на их количестве, — см. `computeWeeklyAggregation`. Поле аддитивное, заполняется в том же цикле, где сейчас считается `workingDays`.
2. Добавить тип `MonthlyRange { firstMonthStart: Date; totalMonths: number }` и функцию `resolveMonthlyRange(customRange, { monthsBefore, monthsAfter })` — точный аналог `resolveWeeklyRange` (`weekly-cell-utils.ts:75`): при валидном `customDateRange` окно растягивается по месяцам, полностью покрывающим диапазон (`startOfMonth`/`endOfMonth`), иначе 3+12 вокруг сегодня.
3. Добавить `generateMonthCellsInRange(range: MonthlyRange, calendarEvents)`. Существующий `generateMonthCells(offset, before, after, events)` **оставить** как тонкую обёртку над ним — «Отделы» продолжают вызывать свою сигнатуру.

**`modules/sections-page/utils/aggregate-bars.ts`**
`computeMonthlyAggregation(loadings, defaultCapacity, dateCapacityOverrides, monthCells)` — копия недельной: сумма ставок и ёмкости по `month.workingDates`, делённая на их количество. Тип `MonthlyAggregation = DailyAggregation`.

✅ Чекпоинт: «Отделы» открываются и выглядят как раньше (месячный режим там использует ту же `generateMonthCells`).

### Этап 2. Общий агрегированный оверлей X/Y

`WeeklyAggregatedBarsOverlay` — 370 строк, месячный отличался бы только словом «неделя». Третью копию не плодим; прецедент — `LoadingBarButton`, вынесенный ровно по этой причине в bug-AB-08.

**Новый `modules/sections-page/components/PeriodAggregatedBarsOverlay.tsx`** — текущий недельный оверлей, обобщённый на тип ячейки:
```ts
interface PeriodCell {
  startDate: string
  endDate: string
  label: string
  workingDates: string[]
  isCurrent: boolean

```
Логика (мини-бар, цвет, inline-редактор, drag за боковые маркеры, `onSaveCapacity` с границами первой и последней ячейки диапазона) переносится **без изменений**.

**`WeeklyAggregatedBarsOverlay`** становится тонкой обёрткой: маппит `WeekCell[] → PeriodCell[]` (`label` = `week.label`, `isCurrent` = `isCurrentWeek`) и рендерит общий компонент. Поведение недельного режима не меняется ни на пиксель.

**Новый `MonthlyAggregatedBarsOverlay`** — такая же обёртка над `MonthCell[]` (`label` = `month.label`, `isCurrent` = `isCurrentMonth`).

⚠️ Это правка кода AB-04, который сейчас в `review`. Регресс маловероятен (маппинг типов, логика не трогается), но недельный режим проверять обязательно.

**`modules/sections-page/components/SectionsPageInternal.tsx`**

Без этого drag ёмкости на год по проекту с десятком разделов упирается в лимит тела server action. Дневной и недельный режимы от правки только выигрывают.

## Риски

1. **Объём upsert-а при drag ёмкости** — снимается этапом 6. Проверить руками: проект с 10+ разделами, протяжка на год.
2. **Общий код с «Отделами»** (`MonthlyHeader`, `monthly-cell-utils`) — все правки аддитивны (опциональные пропы, новое поле, новая функция + обёртка со старой сигнатурой), но «Отделы» прогнать глазами обязательно.
3. **Объединение оверлея (этап 2)** трогает недельный режим, который в review. Проверять оба режима.
4. **Короткие загрузки в месячной сетке** — 1 день ≈ 4.7px при ширине 140. Бар остаётся кликабельным (минимум 4px + tooltip), но подпись не влезет — покажется только ставка. Ожидаемо, совпадает с поведением «Отделов».
5. **Ёмкость затирается молча** — осознанное решение 6. Вероятная будущая жалоба «настроила в дневном, месяц всё сровнял»; лечится потом пометкой месяцев с неравномерной ёмкостью, если всплывёт.
6. **Месячное среднее скрывает неравномерность** — осознанное решение 2. Если начальник отдела начнёт спрашивать «почему месяц зелёный, а люди в первой половине перегружены» — вернуться к варианту с маркером пиковой недели.

## Как решено

Реализовано по плану, все 6 этапов. Отличия от плана и решения, принятые по ходу:

### Новые файлы
- **`modules/sections-page/components/PeriodAggregatedBarsOverlay.tsx`** — общий мини-бар X/Y с inline-редактором ёмкости для широкой сетки. Тип ячейки `PeriodCell { startDate, endDate, label, workingDates }`. Поля `isCurrent` из плана **нет**: оверлей его нигде не читает — подсветку текущей недели/месяца рисуют строки через `getWeekCellClassNames`/`getMonthCellClassNames`, так что поле было бы мёртвым.
- **`modules/sections-page/components/MonthlyAggregatedBarsOverlay.tsx`** — месячная обёртка (именование пропов месячной сетки).

### Изменённые файлы

- **`sections-page/components/WeeklyAggregatedBarsOverlay.tsx`** — стал тонкой обёрткой над общим компонентом (~45 строк вместо 370). Пропы недельной сетки те же, вызывающие строки не менялись.

Введён явный **`isDailyMode = !isWeeklyMode && !isMonthlyMode`**: раньше `!isWeeklyMode` означало «дневной режим», с появлением третьего масштаба это перестало быть верным — все такие места (фоновые ячейки дня, моки) переведены на `isDailyMode`. - **`sections-page/hooks/index.ts`** — `upsertSectionCapacityChunked` (чанки по 1000) как `mutationFn`. Оптимистичное обновление и инвалидация не менялись — они и так применяются ко всему массиву разом.

### Не потребовалось

- Отдельной `computeMonthlyAggregation` — общая `computePeriodAggregation` работает на любом наборе рабочих дат.
- Миграций БД.

## Правки по итогам прогона агентов (Cache / Clean Code / Pragmatic Architect)

- **Чанкованная мутация ломала согласованность кэша при ошибке.** `createCacheMutation` инвалидирует ключи только в `onSuccess`; при падении, скажем, третьего чанка из пяти первые два уже в БД, оптимистика откатывалась к «до жеста», а иерархия живёт со `staleTime: Infinity` — на экране оставались старые числа. Добавлена обёртка `useUpsertSectionCapacityBatch` с `onSettled`-инвалидацией (срабатывает и на успехе, и на ошибке). Текст ошибки при частичной записи теперь честный: «Ёмкость сохранена частично».
- **Ключ оптимистики сужен** с `sectionsPage.all` до `sectionsPage.lists()` — updater безусловно читает `department.projects`, и первый же запрос другой формы под общим префиксом ронял бы `onMutate`.
- **`.select()` убран из `upsertSectionCapacityBatch`** — возвращал до 1000 строк на чанк, потребителя у них нет (оптимистика строится из входа).
- **Тултип столбиков больше не огрубляется** через `decimals`: подпись на строке отдела остаётся «48/52», в тултипе — «47.83 / 52.14». Поправлено и в дневном оверлее.
- **`getTimelineGrid`** (`utils/timeline-grid.ts`) — вычисление режима, ширины и колонок вынесено из четырёх строк иерархии в одну функцию. Колонки неактивных режимов возвращаются пустыми массивами, поэтому флаги `isWeeklyMode &&` перед фоновыми ячейками больше не нужны. Ветки оверлеев ветвятся по самим ячейкам (`weekCells ? … : monthCells ? …`) — так TypeScript сужает типы и `!` нигде не нужен.
- **Enter без правки больше не сохраняет** (`PeriodAggregatedBarsOverlay`): в поле подставляется среднее по периоду, и подтверждение без изменений затирало бы дневную разметку, не меняя число на баре. Растянутый за маркеры диапазон при том же числе сохраняется — это осознанное действие.
- **Стабильная ссылка на пустой календарь** в `SectionsPageInternal` — пока календарь грузится, сетка не пересчитывается на каждый рендер.

Осознанно **не** делалось (решение постановщика): защита от параллельных правок ёмкости, ограничение размера жеста, изменение семантики Y на строке отдела (см. bug-AB-13).

## На что обратить внимание ревьюеру

1. **Обязательно вручную — «Отделы»:** правки в `MonthlyHeader` и `monthly-cell-utils` общие с этой страницей. Все аддитивные, но месячный режим «Отделов» надо открыть и проверить (шапка, скролл, бары) — там `generateMonthCells` теперь вызывает новую внутреннюю функцию.
2. **Обязательно вручную — недельный режим «Разделов»:** `WeeklyAggregatedBarsOverlay` переписан в обёртку над общим компонентом (код AB-04, который сам ещё в review). Логика перенесена дословно, но проверить: мини-бары X/Y, клик по неделе, растягивание диапазона за боковые маркеры, сохранение ёмкости.
3. **Ёмкость в месяце затирает дневные и недельные значения молча** — осознанное решение 6, не баг. Проверить, что клик по месяцу проставляет значение на все дни месяца (видно при переключении в дневной режим), а drag — на весь протянутый диапазон.
4. **Чанкование ёмкости** — при ошибке на середине часть чанков уже записана. Инвалидация подтянет фактическое состояние с сервера, но пользователь увидит «частично сохранилось». Компромисс сознательный: альтернатива — транзакция на стороне БД, это отдельная задача.
5. **Высота строк сотрудника** — правило стекинга то же, что в дневном режиме (этажей = число пересекающихся по датам загрузок), бар ниже (24px против 32px) и без комментариев. Проверить на сотруднике с двумя одновременными загрузками: месячная строка не должна быть выше дневной.
6. **Ширина колонки месяца 98px** — сужена с исходных 140px по просьбе постановщика. Проверить на реальных данных, что не режутся название месяца в шапке («Сентябрь 2026») и подпись столбика на строке отдела («48/52»). Правится одной константой `SECTIONS_MONTH_CELL_WIDTH`.
7. `npm run build` не запускала (правило проекта). Прогнан `npx tsc --noEmit`: **ни один из созданных/изменённых по этой задаче файлов в список ошибок не попал**.
