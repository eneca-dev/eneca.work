# bug-VT-14 Шторм Server Actions при загрузке вкладки «Бюджеты»

При тестировании вкладки «Бюджеты» (Сценарии S1 и S2) вновь обнаружено поведение с водопадом лишних серверных запросов, аналогичное багам `bug-VT-06` и `bug-VT-12`.

### Ожидаемое поведение (по test-VT-05, S1/S2)
При холодной загрузке должно параллельно отправляться всего 3 запроса (`getResourceGraphData`, `getBudgets`, `getSectionCalcBudgets`), которые кешируются на 2-3 минуты или до бесконечности. При возврате на вкладку повторных загрузок быть не должно.

### Фактическое поведение
После нажатия "Загрузить всё" или перехода по вкладкам, помимо загрузки самих данных, в сеть снова улетает пачка из ~15 одинаковых `POST /tasks` запросов.
Главный подозреваемый во всей этой истории — функция `reloadPermissions()`, которая вызывается внутри `useEffect` либо на корневом `TasksView`, либо (что хуже) внутри компонентов-строк. Это приводит к тому, что каждый рендер или маунт спамит сервер. На вкладке "Бюджеты" это усугубляется тем, что данных (`budgets`) очень много, и одновременный шторм экшенов вызывает заметные тормоза и задержки в UI ("долго грузится").

### Как воспроизвести
1. Открыть `/tasks` -> вкладка «Бюджеты».
2. Нажать «Загрузить всё».
3. Проверить вкладку Network (множественные POST-запросы).

### Связанные тикеты
- Обнаружено в рамках [test-VT-05](./test-VT-05.md) (Сценарии S1 и S2).
- Имеет общий корень с [bug-VT-06](./bug-VT-06.md) и [bug-VT-12](./bug-VT-12.md).

## Разбор

«~15 POST» — это разные Server Actions, а не дубли (как в bug-VT-06 / bug-VT-12). В Next.js любой Server Action идёт POST'ом на `/tasks`, различаются заголовком `Next-Action`. `reloadPermissions` не виноват: на старте `BudgetRow` данные не грузит, per-row на маунте нет.

Состав запросов на «Загрузить всё»:
- данные вкладки — 3 легитимных: `getResourceGraphData`, `getBudgets`, `getSectionCalcBudgets` (`useBudgetsHierarchy`);
- глобальный prefetch `<ReferencePrefetch />` (~6, к Бюджетам не относится, 1 раз за сессию);
- опции фильтра + права (~5).

Дублей нет, систематического шторма нет.

## Реальная боль (не «шторм»)

Тормоза «долго грузится» на Бюджетах — это **тяжёлый `getResourceGraphData`**, а не количество запросов. По замеру `EXPLAIN ANALYZE`: `v_resource_graph` = ~19k строк, `select('*')` без проекций, `ORDER BY` по 5 колонкам → внешняя сортировка на диске (~59 МБ), ~1.6с даже в тёплом кэше. На холодном кэше или под конкурентной нагрузкой запрос превышает `statement_timeout` роли `authenticated` (8с) → PostgreSQL отменяет его с кодом `57014` → весь `getResourceGraphData` падает, и вкладка не грузится вовсе (в консоли видно как `[getResourceGraphData] Pagination error: 57014`). Усугубляется параллельной пагинацией (`Promise.all`), запускающей несколько полных прогонов view разом. Лечится отдельной оптимизацией view / проекций / пагинации (убрать `ORDER BY` в JS, убрать `count: 'exact'`, проекция колонок).

Per-row N+1 на Бюджетах (блок «Человеческие ресурсы» при раскрытии проектов) относится к **bug-VT-15**, не сюда.

### Результат ретеста (18.06.2026) - ОТКЛОНЕНО

Тикет возвращен в работу (`todo`). 
Обоснование: Водопад из 15-20 `POST /tasks` запросов при первичной загрузке страницы всё ещё физически присутствует. Оправдание, что это "разные легитимные Server Actions (фильтры, prefetch и т.д.)", не отменяет факта архитектурного недочета. Отправка 20 параллельных XHR/Fetch POST-запросов со стороны клиента при загрузке страницы перегружает пул соединений браузера (вызывая троттлинг сети) и неоправданно спамит сервер. 

**Требуется реальное исправление:**
Необходимо объединять (batching) эти данные на сервере при SSR, либо использовать Server Components для отдачи готового payload'а за один запрос, либо агрегировать prefetch. Водопад запросов на моунте должен быть устранен.

## Контр-анализ ретеста (проверено по коду)

Факты защиты — **подтверждены кодом**; диагноз ревьюера про «пул соединений» — методологически некорректен для прода.

**Подтверждено:**
- **Дублей нет, шторма от `reloadPermissions` нет.** Форсированный `reloadPermissions()` убран — в `TasksView.tsx:33-35` остался только `usePermissionsLoader()` с guard `globalLoadedForUserId` (грузит раз за сессию). Per-row вызовов нет.
- **~15 POST = разные легитимные Server Actions** (в Next.js App Router каждый Server Action — POST на текущий маршрут, различаются заголовком `Next-Action`). Состав: 3 данных вкладки (`getResourceGraphData`/`getBudgets`/`getSectionCalcBudgets`, `use-budgets-hierarchy.ts`) + ~6 `ReferencePrefetch` (глобальный, разово за сессию, отложен через `requestIdleCallback`, последовательно с паузами 300 мс, `staleTime: Infinity`) + ~5 опций фильтра/прав (TanStack Query с кешем и дедупликацией).
- **Реальная боль — тяжёлый `getResourceGraphData`** (`modules/resource-graph/actions/index.ts`): `select('*')` без проекций (`:157-158`), `count: 'exact'` (`:157`), `ORDER BY` по 5 колонкам (`:265-270`), параллельная пагинация `Promise.all` при `PAGE_SIZE=5000` (`:295-299`), **нет обработки `statement_timeout`/`57014`** (на холодном кэше падает с отменой запроса → вкладка не грузится).

**Уточнение к доке выше:** в разделе «Реальная боль» сказано «убрать `ORDER BY` в JS» — фактически сортировка в **SQL** (5 колонок) на 19k-строчной вьюхе без поддерживающего индекса → внешняя сортировка на диске. Суть не меняется.

**Про претензию ревьюера:**
- «15-20 POST перегружают пул соединений браузера» актуально **только на `localhost:3000`** (next dev = HTTP/1.1, лимит ~6 соединений на хост), где запросы сериализуются. На проде (Vercel, HTTP/2 с мультиплексированием) лимит снимается — водопад перестаёт быть узким местом. Тест шёл на dev, отсюда искажение.
- Лечение «SSR / Server Components за один payload» плохо ложится на архитектуру (клиентский TanStack Query + Server Actions + cache-модуль + realtime-инвалидация + клиентские фильтры) — сломает кеширование/realtime/фильтры.

**Вывод:** не закрывать тикет — оправданно (страница реально тормозит/падает), но **по другой причине**. Приоритет: оптимизация самого `getResourceGraphData` (проекции колонок вместо `*`, отказ от `count: 'exact'`, индекс под сортировку, защита от `57014`). Сокращение числа mount-time запросов через батчинг (паттерн `getAllReferenceData` уже есть в проекте) — разумный housekeeping, но вторично. Перенос на SSR — не требуется.
