# feature-EZ-01 Подосновы плановых дат стадий проектирования во вкладке «Разделы»

Родительский тикет. Фича запрошена командой НО/ТЛ для улучшения практичности вкладки «Разделы» в планировщике.

---

## Контекст и проблема

Сейчас РП/ГИП ведут календарные графики (диаграммы Ганта по стадиям проектирования) в Google Sheets вручную — цветные диапазоны дат для ОТР, Стадии А, Стадии С, ЭКО-экспертизы, СТРОЙ-экспертизы и т.д. (см. скриншот-образец в чате).

НО и ТЛ при планировании загрузки сотрудников по разделам:

- не видят, в какой период запланирована та или иная стадия проекта,
- вынуждены вручную собирать эту информацию у РП,
- не могут оценить совокупный запрос на спецов без дополнительных переговоров.

Результат: вкладка «Разделы» без этих данных малопрактична для прогнозирования загрузки.

---

## Что существует в приложении уже сейчас

### Вкладка «Разделы» (модуль `resource-graph`)

- `SectionPeriodFrame` — серый фон с цветными вертикальными границами, отображающий диапазон дат конкретного **раздела** (`section.startDate` / `section.endDate`). Поддерживает drag-to-resize.
- `LoadingBars` — цветные чипы загрузок сотрудников (деком. стадии).
- `PlannedReadinessArea` / `ActualReadinessArea` / `BudgetSpendingArea` — кривые на таймлайне.
- Уже реализована позиционная логика: `calculateBarPosition(startDate, endDate, range)` → `{ left, width }` в пикселях на оси времени.

### Данные о стадиях проектирования

- `projects.stage_id` → ссылка на текущую стадию проекта (параметр, **не** иерархический уровень).
- В БД нет отдельной таблицы с **плановыми датами** каждой стадии проекта. РП ведут их в Google Sheets вне системы.
- Концепция ввода этих дат в приложение была заложена изначально, но функционал скрыт/не активирован (со слов команды разработки).

---

## Что просят добавить

> «Чтобы РП заполняли старт и финиш по проекту (в идеале по разделам), и это светилось подосновой во вкладке "Разделы"»

1. **РП вводит плановые даты стадий проектирования** (старт–финиш) прямо в приложении:

   - Минимум: на уровне проекта (одна строка на стадию: ОТР / Стадия А / Стадия С / ЭКО / СТРОЙ и т.д.).
   - Идеал: на уровне раздела внутри проекта.

2. **Во вкладке «Разделы» эти диапазоны отображаются цветным фоном** (подосновой) под разделами и загрузками.

   - Аналог: цветные строки Google Sheets Ганта из скриншота.
   - Должны быть видны даже без загрузок — как индикатор «этот проект будет в работе в такой-то период».

3. **Практический эффект для НО/ТЛ:**

   - Видят заранее окно активности по каждому проекту.
   - Могут заранее планировать нужное количество спецов.
   - Снижается зависимость от ручного сбора информации у РП.

---

## Варианты реализации

### Вариант A — Минимальный (быстрее)

Добавить к проекту таблицу `project_stage_periods`:

```
project_id | stage_label (текст: "ОТР", "Стадия А", …) | start_date | end_date | color
```

Отобразить в `resource-graph` новым компонентом `ProjectStagePeriodBar` над строками разделов соответствующего проекта. Использовать существующую логику `calculateBarPosition`.

### Вариант B — Полный (логичнее архитектурно)

Переиспользовать или активировать скрытый функционал ввода дат стадий в модуле «Проекты». Связать с `resource-graph` через существующий data-flow (`actions → hooks → TanStack Query`).

---

## Важные ограничения (из обсуждения)

- РП зачастую **сами не знают точных дат** — зависимость от подписания договора, оплаты аванса, наличия ИД и т.д. Поэтому даты должны быть **ориентировочными**, без жёстких обязательств.
- Функционал **полезен хотя бы для уже запущенных проектов**: там даты более предсказуемы.
- **Stage (Стадия) — параметр проекта, не уровень иерархии**. Не создавать новые таблицы, где Stage является родителем для Object/Section.
