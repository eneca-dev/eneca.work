# bug-VT-09 Тяжелый рефетч при изменении данных (drag-to-resize, создание, редактирование)

При выполнении любых мутаций с загрузками на таймлайне (drag-to-resize, создание новой загрузки, редактирование через модалку) происходит отправка лишних Server Actions вместо одного ожидаемого запроса.

### Ожидаемое поведение (test-VT-03, S6)

Должен происходить ровно 1 запрос (Server Action) на сохранение новых дат + должна отрабатывать оптимистичная механика (Optimistic UI) и инвалидация кеша.

### Фактическое поведение

В ходе тестирования сразу после ресайза или создания загрузки в сеть отправляется по 3 `POST http://localhost:3000/tasks` запроса подряд. Это значит, что механизм инвалидации (вероятно `revalidateTag` или `revalidatePath`) работает слишком грубо. После сохранения он заставляет клиент заново скачивать весь массив тяжелых данных (полный рефетч `getDepartmentsData` и других экшенов). Это сильно нагружает сервер и базу при каждом базовом действии (создание, изменение, ресайз).

### Как воспроизвести

1. Открыть `/tasks` -&gt; «Отделы».
2. Изменить загрузку: потянуть за край (ресайз), создать новую (+ Загрузка) или отредактировать существующую.
3. Проверить в Network количество `POST` запросов к `/tasks`.

### Родительская задача

Связано с [test-VT-03](./test-VT-03.md) (Сценарий S6).

## Причины (3 штуки, все подтверждены кодом)

1. `revalidatePath('/tasks')` **+** `revalidatePath('/resource-graph')` — вызывались в каждой мутации загрузки (`modules/modals/actions/loadings.ts`, 6 мест). Подозрение тикета верное. Обе страницы — `force-dynamic` и берут данные из React Query (не RSC), поэтому revalidate ничего не обновлял, только провоцировал лишний RSC-рефетч маршрута.
2. **Двойная инвалидация React Query.** Мутация сама звала `invalidateKeys: [departmentsTimeline.all, ...]`, и параллельно прилетало realtime-эхо от таблицы `loadings`, инвалидируя те же ключи → тяжёлый `getDepartmentsData` рефетчился дважды.
3. **Слишком широкий ключ** `departmentsTimeline.all` (префикс и списка, и freshness) → одна инвалидация дёргала оба запроса, хотя freshness от правки загрузки не зависит. Это же давало «фантомные POST» в bug-VT-07/bug-VT-08.

## Что сделано

- **Убран** `revalidatePath` из всех мутаций загрузок в `modules/modals/actions/loadings.ts` (+ импорт). Данные обновляются через React Query.
- **Сужены ключи инвалидации** `departmentsTimeline.all → departmentsTimeline.lists()` там, где инвалидация вызывает рефетч:
  - `modules/departments-timeline/hooks/index.ts` — `useUpdateLoadingDates`, `useBulkShiftLoadings`;
  - `modules/modals/hooks/useLoadingMutations.ts` — 5 блоков `invalidateQueries` (create/update/split/delete/batch);
  - `modules/cache/realtime/config.ts` — подписка на `loadings`. Теперь freshness команд при правке загрузки не рефетчится. `cancelQueries`/optimistic-снапшоты оставлены на `.all` (операции над кэшем, рефетч не вызывают).

**Эффект:** drag-resize/создание/редактирование — больше нет лишнего RSC-рефетча и рефетча freshness. Optimistic update даёт мгновенный отклик; список обновляется точечно.

## Осталось осознанно (не баг)

Мутация и realtime оба инвалидируют `departmentsTimeline.lists()` — для действующего пользователя возможен повторный фоновый рефетч списка (React Query схлопывает конкурентные запросы по ключу). Ручную инвалидацию намеренно оставили: realtime бывает недоступен (см. bug-VT-16), и мутация — надёжный путь обновления.
