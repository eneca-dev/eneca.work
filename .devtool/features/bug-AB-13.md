# bug-AB-13 Ёмкость Y на строке отдела задваивается между отделами

> Решение отложено осознанно (обсуждено 2026-08-28): выбор варианта меняет смысл строки отдела, поэтому фиксируем и возвращаемся отдельно.

## Симптом

На строке отдела столбик X/Y показывает нехватку людей там, где её нет. Примеры с боевых данных на 2026-08-28:

| Отдел | X (загрузка) | Y (ёмкость) |
|---|---|---|
| ВК | 27.00 | 1.07 |
| АР гражд | 26.95 | 0.40 |
| ОВ гражд | 27.00 | 0.00 |
| КР гражд | 60.25 | 66.20 |

## Причина

`getSectionsHierarchy` (`modules/sections-page/actions/index.ts`) кладёт раздел в дерево **и** отдела-ответственного, **и** отдела каждого сотрудника с загрузкой. Копия несёт **полные** `defaultCapacity` / `capacityOverrides`, а загрузки попадают только в копию отдела сотрудника (условие `employeeDeptId === deptId`).

```
Раздел «Фундаменты», ответственный — отдел КР, ёмкость 2 чел/день
Загрузки:  Иванов (КР) 1.0  +  Петров (ОВ) 1.0

       отдел КР                     отдел ОВ
        └ Фундаменты   Y = 2         └ Фундаменты   Y = 2   ← ёмкость скопирована целиком
           └ Иванов 1.0                 └ Петров 1.0        ← а загрузки разъехались

столбик отдела:  КР → 1.0 / 2 (50%)     ОВ → 1.0 / 2 (50%)
как на самом деле: раздел закрыт полностью, 2.0 / 2 (100%)
Σ Y по компании: 4 вместо 2
```

Итог: X и Y на строке отдела посчитаны по **разным множествам разделов**. X — загрузки сотрудников отдела где угодно; Y — ёмкость всех разделов в дереве отдела, включая те, где отдел только ответственный, а работают чужие.

Масштаб на боевых данных:
- **320 разделов из 4997 (6.4%)** попадают в дерево более чем одного отдела;
- ёмкость на сегодня: реальная **83.20**, суммарная по строкам отделов **111.90** → **+34.5%**.

Внутри одного отдела двойного счёта нет (проверено: `find` по id при построении, `departmentIds` не может содержать один отдел дважды, дедуп строк из bug-AB-12).

## Почему важно

Прямо ломает фичу из коммита «цвета столбиков по нехватке людей» (feature-AB-06 и далее): цвет и процент на строке отдела сейчас недостоверны. Также искажает ввод ёмкости на строке проекта — `handleSaveCapacity` делит введённое значение на количество разделов **в копии этого отдела**, а копии в разных отделах содержат разное число разделов, поэтому одно и то же введённое число даёт разный результат в разных отделах.

## Варианты решения

**(а) Ёмкость только у отдела-ответственного.** В копии для отдела сотрудника `defaultCapacity: 0` / `capacityOverrides: {}`.
```
КР → 1.0 / 2 (50%)    «мой раздел, своими закрыт наполовину»
ОВ → 1.0 / 0 (серый)  «мои люди работают на чужих разделах»
```
Строка отдела отвечает на вопрос «чем заняты **мои люди**». Минус: отдел, который в основном работает на чужих разделах, получает вечно серую строку.

**(б) Ёмкость там, где работают люди отдела** — зеркальный вариант. Хуже: ёмкость раздела «уезжает» в чужой отдел, отдел-ответственный теряет свой показатель.

**(в) Раздел целиком у ответственного; у отдела-сотрудника — только его загрузки, без ёмкости.** ⭐ рекомендация
```
КР → 2.0 / 2 (100%)   ← все загрузки на разделе КР, видно что он закрыт
ОВ → 1.0 / 0 (серый)  ← «мои люди отданы на чужой раздел»
```
X и Y считаются по одному множеству разделов, проценты и цвета становятся честными, Σ Y по компании перестаёт задваиваться. Строка отдела отвечает на вопрос «обеспечены ли **мои разделы**» — это вопрос начальника отдела и ГИПа, ради которых делался месячный вид (feature-AB-11).

## Как проверять после исправления

```sql
-- Σ ёмкости, посчитанная по деревьям отделов, должна сойтись с реальной
WITH tree AS (
  SELECT DISTINCT section_id, dept FROM (
    SELECT section_id, department_id AS dept FROM view_departments_sections_loadings WHERE department_id IS NOT NULL
    UNION ALL
    SELECT section_id, employee_department_id FROM view_departments_sections_loadings
    WHERE loading_id IS NOT NULL AND employee_department_id IS NOT NULL
  ) u WHERE dept IS NOT NULL
), cap AS (SELECT section_id, capacity_value FROM section_capacity WHERE capacity_date = current_date)
SELECT (SELECT sum(capacity_value) FROM cap) AS true_total,
       (SELECT sum(c.capacity_value) FROM tree t JOIN cap c ON c.section_id = t.section_id) AS summed_over_dept_rows;
-- сейчас: 83.20 против 111.90
```
