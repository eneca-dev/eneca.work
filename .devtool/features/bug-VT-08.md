# bug-VT-08 Лишние сетевые запросы при UI-взаимодействиях (фильтрация и сворачивание)

При выполнении сценариев S4 (изменение фильтра) и S5 (раскрытие/сворачивание отделов) на вкладке «Отделы» зафиксированы лишние вызовы Server Actions.

### Ожидаемое поведение (test-VT-03)
- **S4 (Фильтрация):** Должен быть 1 дебаунс-запрос после ввода, а не на каждое нажатие.
- **S5 (Сворачивание/раскрытие):** Это чисто клиентское действие, должно быть **ровно 0 сетевых запросов**.

### Фактическое поведение
В ходе тестирования при вводе фильтра и кликах по сворачиванию/разворачиванию было зафиксировано 3 новых `POST http://localhost:3000/tasks` запроса (Server Actions). Это свидетельствует о том, что:
1. Либо у фильтра сломан дебаунс (запросы улетают на каждый чих).
2. Либо сворачивание/разворачивание компонента вызывает ре-рендер, который почему-то дёргает серверные функции (возможно из-за отсутствия мемоизации или неправильного `useEffect`).

### Как воспроизвести
1. Открыть `/tasks` -> «Отделы».
2. Очистить лог Network.
3. Ввести текст в фильтр (проверить количество запросов).
4. Очистить лог и свернуть/развернуть любой отдел (проверить наличие запросов).

### Родительская задача
Связано с [test-VT-03](./test-VT-03.md) (Сценарии S4 и S5).

## Разбор причины

Проверено по коду.

**S4 (фильтр):** дебаунс есть — `useDebounceValue(localValue, 300)` в `modules/inline-filter/components/InlineFilter.tsx`. `onChange` срабатывает через 300мс после остановки ввода (в т.ч. при вставке и выборе подсказки), и запрос летит только при смене готового токена `queryParams`, а не на каждый символ. Исключение: кнопка «очистить» зовёт `onChange('')` синхронно, минуя дебаунс — но это одиночное действие (1 запрос), не шторм.

**S5 (сворачивание/разворачивание):** операции expand/collapse в `modules/departments-timeline/stores/index.ts` только обновляют Zustand + persist, без Server Actions и инвалидаций. Сворачивание/разворачивание отдела и команды — 0 POST. Единственный сетевой эффект: при первом разворачивании сотрудника монтируется `EmployeeRow`, который тянет `listAllLoadingAccessGrants` — но по статичному ключу, поэтому это ОДИН дедуплицированный запрос на всё дерево, а не per-row N+1.

Зафиксированные «3 POST» — realtime-эхо (широкий префикс `departmentsTimeline.all` инвалидирует при фоновом событии в БД), не следствие фильтрации/сворачивания. Относится к bug-VT-09.
