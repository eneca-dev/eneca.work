# test-VT-03 Тест вкладки «Отделы» (/tasks): сетевые запросы и оптимизация

Родительская задача: **bug-VT-02**. Тестируем по правилам из `bug-VT-02` («Человек + Нейросеть»).

## Цель
Вкладка «Отделы» в модуле `tasks` работает медленно. Цель — разобрать **каждый сетевой запрос** на этой вкладке, найти лишние/дублирующиеся/тяжёлые запросы и предложить оптимизации. Баги/находки оформляем отдельными тикетами `bug-...`.

## Контекст реализации (для проверяющего ИИ)
- Маршрут: `app/(dashboard)/tasks/page.tsx` → `TasksView` → при `viewMode === 'departments'` рендерит `DepartmentsTimelineInternal` (модуль `modules/departments-timeline`).
- Server Actions в Next.js App Router идут как **POST на текущий маршрут `/tasks` с заголовком `Next-Action`** — различаем их по этому заголовку и по телу ответа.
- Ожидаемые запросы при работе вкладки:
  - `getDepartmentsData(filters)` — основная тяжёлая выборка (орг.структура + `view_employee_workloads` + гранты). `staleTime: Infinity` (обновление только через Realtime/invalidation).
  - `getTeamsFreshness()` — актуальность команд, `staleTime: 5 мин`.
  - `useCompanyCalendarEvents` (из `resource-graph`) — события календаря компании.
  - `reloadPermissions()` — вызывается в `TasksView` на маунте (useEffect) → возможный источник лишних запросов/рефетча.
- Мутации и их инвалидация:
  - `updateLoadingDates` (drag-resize) → optimistic + invalidate `departmentsTimeline.all` + `sectionsPage.all`.
  - `bulkShiftLoadings` → N апдейтов `loadings` батчами по 10 + invalidate тех же ключей.
  - `confirmTeamActivity` / `confirmMultipleTeamsActivity` → invalidate `freshness`.
- Realtime-подписки модуля (см. `modules/cache/realtime/config.ts`).

## Среда
- `localhost:3000`, dev-режим, тестировщик авторизуется сам.
- Браузер открывает ИИ через Playwright MCP; тестировщик кликает в этом окне.
- ИИ читает console + network через Playwright, состояние БД — через Supabase MCP (только чтение).

## Сценарии (чек-лист)

### 🔴 Приоритет 1 — базовый сетевой профиль
- [ ] **S1. Холодная загрузка вкладки.** Открыть `/tasks`, переключиться на «Отделы».
  - Зафиксировать: список всех запросов, по каждому — метод, статус, время ответа, размер.
  - Ожидание: `getDepartmentsData` — 1 раз, `getTeamsFreshness` — 1 раз, календарь — 1 раз.
  - Искать: дубли (особенно двойной `getDepartmentsData` из-за `reloadPermissions` на маунте), лишние запросы, водопад вместо параллели.
- [ ] **S2. Переключение вкладок Отделы → Канбан → Отделы.**
  - Ожидание: при возврате `getDepartmentsData` НЕ перезапрашивается (`staleTime: Infinity`, кеш-хит).
  - Искать: лишний рефетч при возврате, повторный `reloadPermissions`.
- [ ] **S3. Размер и время `getDepartmentsData`.**
  - Измерить размер ответа и время; в Supabase/Sentry — длительность `db.query`.
  - Искать: over-fetch (`select('*')` на вьюхах), непропорционально большой payload, N+1 на сервере.

### 🟡 Приоритет 2 — реакция на действия пользователя
- [ ] **S4. Изменение фильтра** (например `отдел:"..."`).
  - Ожидание: запрос уходит на закоммиченный фильтр, есть дебаунс, нет запроса на каждый символ.
  - Искать: запрос-на-keystroke, дубли при одном изменении, гонки.
- [ ] **S5. Раскрытие/сворачивание отдела/команды/сотрудника.**
  - Ожидание: **ноль** сетевых запросов (чистый клиент, UI-store).
  - Искать: любой запрос здесь = баг/лишняя нагрузка.
- [ ] **S6. Drag-to-resize загрузки** (`updateLoadingDates`).
  - Ожидание: 1 экшен на сохранение + optimistic UI; затем инвалидация.
  - Искать: тяжёлый полный рефетч `getDepartmentsData` после каждого ресайза (главный кандидат на оптимизацию), повторные запросы.

### 🟢 Приоритет 3 — фон и массовые операции
