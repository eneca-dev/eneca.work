# bug-SB-05 Снять налог `getFilterContext` — локальная валидация JWT (`getClaims`) + пул соединений

## Проблема

Это **корень**, на который указывали SB-01 / SB-03 / SB-04: почти каждый серверный экшен сначала проходит «гейт» `getFilterContext`, а тот **первым делом** делает **сетевой** `supabase.auth.getUser()` — round-trip к Supabase Auth (GoTrue) для валидации JWT.

```ts
// modules/permissions/server/get-filter-context.ts:50
const { data: { user } } = await supabase.auth.getUser()  // ← сетевой вызов на КАЖДЫЙ экшен
```

- `getFilterContext()` зовётся в **25 местах / 15 файлах** (+ `getFilterContextTasks`, + `getRestrictedProjectIds`, который сам идёт через тот же контекст).
- Когда экран открывает **пачку** экшенов сразу — каждый платит этот auth-round-trip и борется за соединение в пуле.

**Где это видно (замеры):**
- **Модалка «Создать загрузку»** при открытии стреляет пачкой: `fetchProjectsListRPC` (список) + `fetchProjectTree` (дерево) + `fetchBreadcrumbs` (путь). В Network: breadcrumbs **1.73с** при ответе **0.7 кБ** (данных нет — время съел auth/пул), дерево 990мс, плюс 6× `fetch.js` по 0.6–1.24с. Префетч дерева/списка (см. ниже) убирает **один** запрос из пачки, остальные всё равно платят свой `getFilterContext`.
- **Бюджеты (SB-01)** и **фильтр Задач (SB-04)**: разобрано по Sentry (35 250 вызовов `getFilterContext` за 7д) — **медиана 136мс, p95 760мс**, но **редкий хвост 13–32с** (3 из 35 250) от сатурации пула / `auth.getUser` под нагрузкой (в трейсе `view_users` и RPC висели по 30с одновременно, а БД отвечала мгновенно). Это **инфраструктура, не код конкретной вкладки** — поэтому лечится здесь, а не префетчами в каждом модуле.

Запросы **внутри** `getFilterContext` уже быстрые (RPC permissions ~7мс, `view_users` ~1мс) и параллелятся через `Promise.all`; сам контекст уже дедуплицируется (bug-VT-06). Остаётся снять две системные статьи расхода: **сетевой `auth.getUser`** и **дефицит соединений под burst**.

## План

### 1. Пул соединений — *(делает Саша, инфра)*
Transaction-пулинг (Supabase pooler / pgBouncer, порт 6543) для серверных экшенов → burst из N параллельных экшенов перестаёт упираться в лимит прямых соединений; уходит хвост 13–32с и HTML-ответы шлюза вместо JSON (см. SB-04). **Вне кода этого тикета.**

### 2. Локальная валидация JWT: `auth.getUser()` → `auth.getClaims()` — *(код)*
`getClaims()` проверяет **подпись и `exp` JWT локально** (по кэшированному JWKS), без сетевого round-trip к GoTrue. supabase-js `^2.49.4` его поддерживает.

- В `get-filter-context.ts` (Phase 0) и `get-filter-context-tasks.ts` заменить `auth.getUser()` на `auth.getClaims()`; `user.id` → `claims.sub`. Регэксп-валидация UUID и все последующие запросы остаются как есть.
- Безопасность **не слабее**: невалидный/просроченный токен так же отбивается (подпись + `exp` проверяются локально). RLS на стороне БД (`auth.uid()` из JWT) **не затрагивается** — меняем только способ валидации на сервере приложения, не на стороне Postgres.
- Проверить остальные «горячие» экшены на прямой `auth.getUser()` (`getRestrictedProjectIds` и т.п.) и перевести по тому же принципу.

> **⚠️ Предусловие (без него выигрыша нет).** Локальная валидация `getClaims` работает только если проект Supabase использует **асимметричные JWT-ключи** (ECC/RSA, фича «JWT Signing Keys»). На легаси-секрете (HS256) `getClaims` падает обратно в сетевой `getUser`. → Сначала в Supabase Dashboard → Auth → JWT Keys мигрировать на асимметричный ключ (ротация без разлогина активных сессий — проверить на стейдже). **Это первый шаг тикета.**

### 3. Подчистить временные митигации модалки «Создать загрузку» — *(после 1+2)*
Пока корень не снят, уже сделаны **частичные** обходы (прячут симптом, греют/переиспользуют кэш, но не убирают `getFilterContext`-налог). Когда каждый экшен станет дешёвым — упростить/пересмотреть:

**Префетч (idle, после отрисовки страницы — на «Разделах» и «Отделах», модалка общая):**
- `usePrefetchProjectsList` — греет списки `'my'` + `'all'`, затем **деревья «Моих» проектов** (ограниченный набор), последовательно → «Мои» проекты раскрываются в модалке без загрузки. «Все» деревья не греем (~132 = шторм).
- `usePrefetchProjectTrees` + `projectTreeQueryOptions` — дополнительно (только «Разделы») греет деревья **раскрытых** проектов (id переживают перезагрузку в localStorage).
- Всё последовательно (один `getFilterContext` ~1с на запрос). На «Отделах» tree-префетч раскрытых проектов не нужен — там иерархия `Отдел→Команда→Сотрудник`, проектов в раскрытии нет.

**Cache-first чтение из уже прогретого дерева** (убирает 2 из ~4 холодных запросов при открытии модалки, когда дерево тёплое):
- `modules/modals/hooks/project-tree-cache.ts` — `findBreadcrumbsInCache` / `findSectionStagesInCache` читают закэшированные деревья (`['projects','detail',*,'tree']`);
- `useBreadcrumbs` — breadcrumbs из дерева вместо `fetchBreadcrumbs` (иначе фолбэк на запрос);
- `useDecompositionStages` — этапы раздела из дерева вместо `fetchDecompositionStages` (иначе фолбэк);
- парная инвалидация `decompositionStages.all` в `useDecompositionStageMutations` / `useUpdateDecompositionStage` (синхрон cache-first с деревом).
- `gcTime: Infinity` + `staleTime 5 мин` на модальных кэшах (дерево/список/этапы/breadcrumbs): кэш **не удаляется** в течение сессии, поэтому модалка открывается **без крутилки** — старые данные показываются сразу, а свежие тихо подтягиваются в фоне (stale-while-revalidate). Раньше gcTime 10 мин удалял кэш → после простоя был холодный спиннер.

Ограничение всех этих обходов: для **непрогретого** проекта модалка всё равно грузит дерево/список и платит `getFilterContext`. Полностью «из кэша» и мгновенно — только после этого тикета. Решить при ревью: оставить как доп-ускорение или упростить.
