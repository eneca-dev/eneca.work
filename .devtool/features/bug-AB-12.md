# bug-AB-12 Дубли загрузок на странице «Разделы» из-за пагинации без сортировки

## Симптом

В консоли пачка одинаковых ошибок React (наблюдалось 24 штуки за один рендер):

```
Encountered two children with the same key, `a69668de-...`.
  at WeeklyLoadingBars (components/shared/timeline/WeeklyLoadingBars.tsx:172)
  at EmployeeRow (modules/sections-page/components/rows/EmployeeRow.tsx)
```

Появляется не всегда — «то есть, то нет» между перезагрузками страницы.

## Причина

`getSectionsHierarchy` (`modules/sections-page/actions/index.ts`) читает `view_departments_sections_loadings` **страницами по 1000 строк** через `.range()`, но **без `ORDER BY`**.

PostgreSQL не гарантирует одинаковый порядок строк между отдельными запросами, если сортировка не задана явно (план запроса, параллельные воркеры, конкурентная запись между страницами). Поэтому соседние страницы могут **перекрыться** — одна строка приходит дважды — и одновременно **потерять** другие.

Продублированная строка проходит весь трансформ и дважды пушится в `objectSection.loadings` → у сотрудника две загрузки с одинаковым `id` → React ловит одинаковые ключи в `WeeklyLoadingBars`.

Проверка на реальных данных:
- вью отдаёт **9102 строки** → 10 страниц, пагинация заведомо активна;
- `loading_id` во вью **уникален** (5608 строк с загрузкой = 5608 разных id) — то есть дублей на стороне БД нет, они появляются именно при постраничном чтении;
- пара `(section_id, loading_id)` уникальна на всех 9102 строках — годится как детерминированный ключ сортировки.

### Почему заметили только сейчас

Баг старше недельного вида. В дневном режиме ключ бара — `${bar.period.id}-${idx}`, индекс делает его уникальным, и React молчит. Но дублированная загрузка при этом:
- **рисуется дважды** (полоски лежат друг на друге, визуально незаметно);
- **дважды попадает в сумму X** на мини-барах X/Y (`computeDailyAggregation` идёт по массиву загрузок) — то есть занятость раздела/проекта/отдела показывалась завышенной.

Недельный (и теперь месячный) режим использует `key={bar.loading.id}` без индекса — он не создал баг, а сделал его видимым.

## Решение

`modules/sections-page/actions/index.ts`, два изменения:

1. **Детерминированный порядок перед пагинацией** — корневое исправление:
```ts
query = query
  .order('section_id', { ascending: true })
  .order('loading_id', { ascending: true, nullsFirst: true })
```
Пара уникальна во вью, значит порядок строк полный и одинаковый для всех страниц.

2. **Дедупликация строк после сборки страниц** — страховка: фильтр по ключу `${section_id}|${loading_id ?? ''}`. Если порядок всё же «поедет» (сменится план, придёт конкурентная запись между страницами), задвоенная строка не дойдёт ни до `loadings`, ни до счётчиков, ни до агрегаций. Расхождение количества логируется в Sentry как warning — чтобы было видно, если страховка реально сработала.

Дедуп сделан на уровне сырых строк, а не при пуше в `objectSection.loadings`, потому что дублированная строка портит не только массив загрузок: она же накручивает `totalLoadings`, `dailyWorkloads` и активность проекта для сортировки.

3. **`PAGE_SIZE` 1000 → 5000** (db-max-rows проекта): на текущих ~9k строк это 2 запроса вместо 10, то есть окно, в котором конкурентная вставка может сдвинуть постраничную выборку, уже в 5 раз. Инвариант выхода из цикла (`page.length < PAGE_SIZE`) продолжает работать. `MAX_PAGES` пересчитан с 200 на 40 — тот же потолок в 200k строк.

4. **`rows` переприсваивается, а не мутируется** через `push(...uniqueRows)`: спред до 200k аргументов (потолок цикла) роняет движок с `RangeError`.

### Что этим НЕ лечится

Offset-пагинация страдает и обратным эффектом: вставка строки с меньшим `section_id` между запросами страниц сдвигает окно и **теряет** строку — дедуп такого не увидит. Полное решение — keyset-пагинация (`.gt('section_id', last)`), но для ~9k строк в 2 запроса это избыточно. Окно гонки сужено настолько, насколько это дёшево.

## На что обратить внимание ревьюеру

1. **Обязательно вручную:** открыть «Разделы» без фильтров (9к+ строк → пагинация точно работает), перезагрузить несколько раз — ошибок про одинаковые ключи быть не должно ни в одном из трёх режимов.
2. Проверить, что числа X на мини-барах не изменились в меньшую сторону **неожиданно сильно**: если раньше какая-то загрузка задваивалась, теперь X станет меньше — это исправление, а не регресс, но стоит убедиться, что цифры выглядят правдоподобно.
3. Сортировка добавлена в запрос — порядок строк во вью меняется, но иерархия строится через `Map`/`find` по id и от порядка строк не зависит. Порядок отделов/проектов на экране задаётся отдельной сортировкой (`sort-projects.ts`), её это не трогает.
4. **Найдено, но не исправлено (вне объёма этой задачи):** такой же постраничный паттерн есть в `modules/resource-graph/actions/index.ts`, `modules/budgets/actions/budget-actions.ts`, `modules/budgets-page/actions/budget-hierarchy.ts`. Там `.order()` есть, но по НЕуникальному набору полей (`project_name`, `object_name`, `section_name`, …) — при равных значениях порядок внутри группы всё ещё не определён, и страницы теоретически могут разъехаться. Плюс страницы там читаются параллельно. Если такие же дубли всплывут на «Графике ресурсов» или в бюджетах — причина будет та же, лечится добавлением уникального поля последним ключом сортировки.
